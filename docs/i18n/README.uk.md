iCloud Drive, Dropbox, OneDrive, Google Drive і Syncthing синхронізують файли по одному. Git же розраховує, що каталог `.git` змінюється як єдине ціле, тому в репозиторії всередині синхронізованої теки з'являються конфліктні копії на кшталт `.git/index 2` і `refs/heads/main 2`, зниклий index поруч із забутим `index.lock` та об'єкти, які існують лише в хмарі. FAQ самого git застерігає від зберігання репозиторіїв у синхронізованих теках, але налаштування за замовчуванням і далі кладуть їх туди: «Робочий стіл» і «Документи» в iCloud на macOS, резервне копіювання тек в OneDrive на Windows, `Documents/GitHub`.

<p align="center">
  <img src="../../assets/sync-damage.svg" width="820" alt="Клієнт синхронізації копіює .git між пристроями файл за файлом і залишає конфліктні копії на кшталт index 2 та refs/heads/main 2, index.lock поруч зі зниклим index та об'єкти, що є лише в хмарі">
</p>

`gitbrella check` зазвичай менш ніж за секунду повідомляє, чи має репозиторій такі пошкодження. Його створено для запуску до того, як ШІ-агент або git-хук торкнеться репозиторію. `gitbrella fix` виправляє те, що має рівно один правильний спосіб відновлення, а `gitbrella move-out` усуває пошкодження в корені: переносить `.git` за межі синхронізованої теки й залишає на його місці файл `.git`, що вказує туди, тож клієнт синхронізації переносить ваші файли, а git тримає історію в себе.

| Команда | Що робить |
| --- | --- |
| `gitbrella check` | повідомляє про пошкодження (лише читання) |
| `gitbrella fix` | виправляє те, що має одну правильну відповідь |
| `gitbrella move-out` | назавжди виносить `.git` із синхронізованої теки |
| `gitbrella undo` | скасовує останнє виправлення чи перенесення |
| `gitbrella history` | перелік змін, зроблених на цьому пристрої |
| `gitbrella prune-backups` | видаляє старі резервні копії змін, які вже не можна скасувати |
| `gitbrella hook --for claude\|codex` | захищає виклики інструментів ШІ-агента |

## Швидкий старт

**1. Перевірити.** Лише читання, без завантажень і без мережі.

```sh
cd ~/Library/Mobile\ Documents/com~apple~CloudDocs/notes
gitbrella check               # код 0: усе гаразд, 1: пошкодження, 2: не вдалося запустити
```

**2. Виправити.** Лише те, що має одну правильну відповідь. Без `--apply` тільки показує план.

```sh
gitbrella fix                 # що буде виправлено і що залишиться вам
gitbrella fix --apply         # виправити; `gitbrella undo --apply` поверне як було
```

**3. Вирішити назавжди.** Винести `.git` із синхронізованої теки.

```sh
gitbrella move-out            # що станеться і що може завадити
gitbrella move-out --apply
```

**Залишатися захищеним.** Блокувати коміти в пошкодженому репозиторії:

```sh
printf '#!/bin/sh\nexec gitbrella check\n' > .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit
```

Для ШІ-агентів див. [Для агентів](#for-agents).

## Що гарантується

- <img src="../../assets/icons/read-only.svg" width="18" alt=""> **`check` лише читає.** Він ніколи не пише в репозиторій. Git запускає лише команди читання, з `GIT_OPTIONAL_LOCKS=0` і вимкненими автоматичним gc та обслуговуванням. Наскрізні тести для ризикових випадків (копія index, зниклий index, частковий клон, розділений index, перенесений каталог git) записують розмір, mtime та inode кожного файлу до і після перевірки й порівнюють їх.
- <img src="../../assets/icons/no-download.svg" width="18" alt=""> **Нічого не завантажує з хмари.** На macOS він вимикає завантаження на вимогу для свого процесу (і git, який запускає), перш ніж торкнутися диска; якщо macOS відмовляє, перевірка не запускається (код 2). Файл, що є лише в iCloud, потрапляє у звіт, але не завантажується.
- <img src="../../assets/icons/no-network.svg" width="18" alt=""> **Не звертається до мережі.** Частковий клон ніколи не довантажує відсутні об'єкти (`GIT_NO_LAZY_FETCH`); з git, старішим за 2.45, перевірки об'єктів натомість пропускаються.
- <img src="../../assets/icons/quiet.svg" width="18" alt=""> **Мовчить на здорових репозиторіях.** Блокування вважається пошкодженням, лише якщо воно старе і жоден git, що працює з цим репозиторієм (з будь-яким його робочим деревом), не міг його записати: git створює блокування, коли бере його, тож git, запущений пізніше, не може його утримувати. Тимчасові файли git і файли інших інструментів усередині `.git` — інформаційні. Запуск на 89 здорових робочих репозиторіях не виявив жодного пошкодження.

<a name="usage"></a>

## Використання

```
gitbrella check [--json] [--deep] [--provider NAME] [path]
```

Коди виходу: **0** пошкоджень немає, **1** знайдено пошкодження, **2** перевірку не вдалося виконати. Для команд, що щось змінюють (`move-out`, `fix`, `undo`): **0** заплановано, виконано або нічого робити (`already`), **1** відмова (з причинами), виконано з попередженнями або залишилися пошкодження, залишені вам (список MANUAL у `fix`; `check` і далі про них повідомляє), **2** збій (відкат або зупинка; JSON зберігає те, що вдалося відновити, і записи журналу) або не вдалося запустити.

`--deep` додатково запускає повний `git fsck` (він читає всі об'єкти, тому пропускається, якщо об'єкти є лише в хмарі). `--provider` задає клієнт синхронізації замість визначення за шляхом: `auto` (за замовчуванням), `icloud`, `icloud-desktop-documents`, `dropbox`, `onedrive`, `google-drive`, `syncthing`, `nextcloud`, `cloud-storage`, `none`. Теки Syncthing і Nextcloud (або ownCloud) розпізнаються будь-де за маркером, який клієнт кладе всередину (`.stfolder`, `.sync_*.db`). `fix` і `move-out` приймають той самий `--provider`; передайте те саме значення, що й `check`, бо деякі імена копій враховуються лише для певного клієнта. У JSON тоді буде `"providerForced": true`.

### Як git-хук

```sh
#!/bin/sh
# .git/hooks/pre-commit
exec gitbrella check
```

<p align="center">
  <img src="../../assets/hook-flow.svg" width="820" alt="git commit запускає хук pre-commit, який запускає gitbrella check: при коді 0 коміт проходить, при 1 або 2 його заблоковано">
</p>

У пошкодженому репозиторії коміт блокується, у здоровому проходить як звичайно. Інструмент знає, що хук запустив git, і не плутає власне блокування коміту зі старим.

**Який репозиторій перевіряється.** У хуках коміту (git передає їм `GIT_INDEX_FILE` або абсолютний `GIT_DIR`) репозиторій знаходиться за процесом git, що запустив хук, тому хук може спершу змінити каталог: на каталог git, його каталог hooks або каталог поза будь-яким репозиторієм. Коли git вказує репозиторій через абсолютний `GIT_DIR` (пов'язане робоче дерево, підмодуль, відокремлений каталог git), кожна команда git у хуку працює з ним, куди б хук не перейшов, і перевірка теж. В інших випадках перевіряється, куди веде поточний каталог для самого git (каталог git, на який там вказує відносний `GIT_DIR`, або репозиторій, знайдений звідти); якщо це інший репозиторій або інше робоче дерево того самого репозиторію (хук, що туди переходить, чи редактор повідомлення коміту), перевірка відмовляє (код 2), а не відповідає за чужий репозиторій.

Без шляху перевіряється репозиторій, який git експортував хуку (`GIT_DIR`), тож працюють і dotfiles-конфігурації з `--git-dir`, і каталог git усередині власного робочого дерева. Без шляху враховується й `GIT_DIR`, заданий в оболонці; на відміну від git, неіснуючий `GIT_DIR` ігнорується, а пов'язане робоче дерево, за яким неможливо пройти, відхиляється замість того, щоб вважати робочим деревом поточний каталог.

**Index, який записує коміт.** Якщо `GIT_INDEX_FILE` вказує на файл усередині каталогу git (так git робить для хуків коміту), читається саме він. Якщо index, який запише коміт, відсутній або порожній, або більше не перелічує файли HEAD, що ще лежать у робочому дереві, коміт блокується до того, як запише їх видалення. Файл index в іншому місці, вказаний вами через `GIT_INDEX_FILE`, не читається: усередині хука замість нього перевіряється власний index репозиторію, а ручна перевірка з цією змінною відхиляється (код 2).

**Навмисні видалення.** Щоб припинити відстежувати файли, які залишаться на диску (`git rm --cached`, припинення відстеження каталогу, що тепер ігнорується), або навмисно закомітити «видалити все», поки файли ще на диску (`git rm -r --cached .`), пропустіть хук за допомогою `git commit --no-verify`.

### З менеджером хуків

- **pre-commit** (pre-commit.com): додайте цей репозиторій з id хука `gitbrella` (pre-commit збере його на Go) або `gitbrella-system` (бінарник із PATH); див. `.pre-commit-hooks.yaml`.
- **lefthook**: підключіть `hooks/lefthook.yml` через `remotes`.
- **husky**: `.husky/pre-commit`, що містить `gitbrella check`.
- **Overcommit**: `PreCommit: { Gitbrella: { enabled: true, required_executable: gitbrella, command: [gitbrella, check] } }`, потім `overcommit --sign`.

У всіх них будь-який ненульовий код зупиняє коміт, тож перевірка, яка не змогла запуститися (код 2), теж його зупиняє. Aider комітить з `--no-verify`, якщо не задано `git-commit-verify: true`, і тоді жоден хук коміту не запускається. Obsidian Git (десктоп) комітить системним git і запускає хук; додайте теку з `gitbrella` до його налаштування «Additional PATH», бо застосунки, запущені з Dock, не отримують PATH оболонки. Obsidian Git на мобільних (isomorphic-git) хуків не запускає.

<a name="for-agents"></a>

### Для агентів

`--json` виводить той самий звіт як стабільний версійований документ (`schemaVersion: 1`, `findings` завжди список). Ухвалюйте рішення за кодом виходу й показуйте знахідки користувачеві.

Власні хуки агентів зупиняють виклик інструмента лише при коді 2: код 1 («знайдено пошкодження») пропускає виклик. `gitbrella hook --for claude|codex` говорить мовою їхніх хуків. Він читає подію, яку агент передає через stdin:

<p align="center">
  <img src="../../assets/agent-hook.svg" width="820" alt="Виклик інструмента агентом проходить через gitbrella hook: читання й редагування тривають; у пошкодженому репозиторії запис через git і запис у .git зупиняються кодом 2">
</p>

- **Перед викликом інструмента** (`PreToolUse`): у пошкодженому репозиторії команда git, що пише (commit, add, reset, rebase, push і все, про що невідомо, що воно лише читає), і запис у `.git` зупиняють виклик (код 2, причина для агента в stderr). Читання, редагування ваших файлів, `git restore` і сам `gitbrella` тривають, щоб пошкодження можна було оглянути й виправити.
  - *Непридатні репозиторії.* Там, де файли git є лише в хмарі або git узагалі не може використати репозиторій (перейменований `HEAD`, файл `.git`, що вказує в нікуди), зупиняється кожна команда git: вона б зависла або подіяла на зовнішній репозиторій. Запис у `.git` там триває: таке виправлення робиться вручну всередині `.git`, як сказано в причині (`mv '.git/HEAD 2' .git/HEAD`). Засіб, названий у підказці `core.worktree` (`git config --file … --unset core.worktree`), теж триває.
  - *Який репозиторій.* Той, що містить файли, з якими працює виклик (патч Codex називає свої файли; шлях усередині `.git` належить робочому дереву над ним). Для команди оболонки — тека сесії та кожна тека, у якій виконуються її команди git (`cd DIR`, `pushd`, `git -C DIR`, `--git-dir`, `--work-tree`, `GIT_DIR`, `env -C`, `bash -c '…'`), спершу ті, що пишуть, не більше п'яти; якщо та, що пише, не вміщується, виклик проходить із попередженням. Кожну теку оцінюють за тим, що виклик у ній робить: `git -C ../sound commit` із пошкодженої теки сесії триває. Тека, що не є репозиторієм, і bare-репозиторій проходять мовчки.
  - *Коли перевірку не вдається запустити.* Усе, що заважає перевірці виконатися (зокрема 20-секундний `--timeout` — єдиний строк на весь виклик), пропускає виклик із попередженням; `--fail-open` робить те саме там, де git не може використати репозиторій.
  - *Як читається команда.* Вона читається, але ніколи не виконується: лапки, коментарі, підоболонки, підстановки (зокрема всередині heredoc без лапок), heredoc, змінні, які вона задає, `&&`, `||`, `if`, `case` і цикли (після `cd a || cd b` або `cd` у неіснуючу теку враховується кожна тека, де може опинитися оболонка; цикл `for` читається по разу для кожного значення), обгортки (`timeout`, `sudo`, `nice`, `xargs`, `env`) і скрипти, передані оболонці (`-c`, `eval`, `watch`, `source`, файл, heredoc, `bash < f`, конвеєр у `sh`). Функції та аліаси, визначені командою, читаються там, де їх викликають. Скрипт оболонки, запущений за шляхом або переданий оболонці (`./deploy.sh`, `bash deploy.sh`), читається, якщо це невеликий файл на цій машині (зокрема через симлінк; один раз, навіть якщо він запускає сам себе); `make`, `npm run` і подібні не читаються.
  - *Що вважається записом.* Запис іншої програми в `.git` (`rm .git/index.lock`, `> .git/HEAD`, `cd .git && rm index.lock`, `sed -i` для `.git/config`, `rm -rf` або `find -delete` для теки, що містить `.git`, патч Codex через оболонку) вважається записом у `.git`; копіювання `.git` деінде, пакування в `tar` чи читання — ні. `gh pr checkout` і `git-lfs` вважаються командами git, що пишуть.
  - *У разі сумніву.* Кожне з наведеного вважається командою git, що пише: читання, довше за 5000 кроків або половину `--timeout` (у теці, яку не вдалося визначити); слово `git` там, куди читання не стежить; скрипт, переданий конвеєром в оболонку з програми, за якою читання не стежить (`curl … | sh`), там, де він виконується; наявний, але непрочитний скрипт, переданий оболонці (завеликий, лише в хмарі), там, де він виконується. Якщо не вдається визначити, у яку теку пише команда git (`cd "$(…)"`, `for d in */`), вона враховується в кожній перевірюваній теці, а виклик отримує попередження.
- **На початку сесії** (`SessionStart`): один рядок у stdout, який агент читає як контекст: що репозиторій розташований у синхронізованій теці (якщо його каталог git ще не винесено) і що пошкоджено. Ніколи не блокує.

Хук нічого не змінює. Для Claude Code у `.claude/settings.json`:

```json
{
  "hooks": {
    "SessionStart": [{"hooks": [{"type": "command", "command": "gitbrella hook --for claude"}]}],
    "PreToolUse": [{"matcher": "Edit|Write|MultiEdit|NotebookEdit|Bash",
                    "hooks": [{"type": "command", "command": "gitbrella hook --for claude"}]}]
  }
}
```

Для Codex у `.codex/hooks.json` (Codex запускає хук лише після того, як ви довіритеся йому в `/hooks`):

```json
{
  "hooks": {
    "SessionStart": [{"hooks": [{"type": "command", "command": "gitbrella hook --for codex"}]}],
    "PreToolUse": [{"matcher": "Bash|apply_patch",
                    "hooks": [{"type": "command", "command": "gitbrella hook --for codex"}]}]
  }
}
```

Перевірка виконується по одному разу для кожної з цих тек, зазвичай по 0,1–0,4 секунди, тому патч, що зачіпає кілька тек одного репозиторію, перевіряє цей репозиторій кілька разів; `--timeout` обмежує весь виклик.

<a name="repairing"></a>

## Відновлення

```sh
gitbrella fix                 # що буде виправлено і що залишиться вам
gitbrella fix --apply         # виправити
gitbrella undo --apply        # повернути все як було
gitbrella history             # зміни, зроблені тут, їхні резервні копії та розміри
gitbrella prune-backups       # резервні копії, які вже не потрібні жодному undo
```

<p align="center">
  <img src="../../assets/fix-flow.svg" width="820" alt="fix показує план; fix --apply записує кожен крок, потім перевірка запускається знову: готово або відкат; undo --apply скасовує останню зміну">
</p>

`check` зазначає під кожним пошкодженням, чи виправить його `fix` (`repair:` та `"repair": "fix"` або `"manual"` у JSON), і називає `fix --provider NAME`, якщо перевірці було задано провайдера. Усередині хуків коміту він нічого не питає.

`fix` виправляє лише там, де є одна правильна відповідь і нічого, що ви могли мати на увазі, не перезаписується:

| Пошкодження | Виправлення |
| --- | --- |
| конфліктні копії в `.git` поруч з оригіналом (`HEAD 2`, `refs/heads/main 2`, `refs 2`, `packed-refs 2`, копії Dropbox і Syncthing, а також копія блокування ref, наприклад `refs/heads/main 2.lock`); копія index — лише якщо вона ідентична index або є коректним index, що дорівнює HEAD | переміщуються до резервної копії; об'єкт (коміт, тег, дерево чи файл), на який вказує лише копія, спершу зберігається як `refs/gcd-rescue/<name>` |
| залишений каталог rebase, `desktop.ini`, `Icon` та подібні файли, створені не git (якщо тільки git не читає їх як гілку або їхнє ім'я не є іменем об'єкта), копія `.git` у робочому дереві, коміти якої вже є в репозиторії | переміщуються до резервної копії |
| відсутній index без копій і блокувань будь-де | створюється з HEAD (`git read-tree HEAD`: файли не зачіпаються), лише якщо є коміт, на основі якого його будувати (якщо коміт HEAD теж відсутній, його спершу довантажують, як описано нижче), і поза sparse checkout |
| index, що не перелічує жодного файлу (коректний, нерозділений index поза sparse checkout) | переміщується до резервної копії й створюється з HEAD: у ньому нічого не було підготовлено до коміту |
| осиротілий `index.lock`, що є коректним index, рівним HEAD | стає index |
| порожній файл гілки | коміт, який останнім записав її reflog |
| `.git.nosync`, який git додав би до коміту | рядок `/.git.nosync/` у `.git/info/exclude` |
| відсутній коміт HEAD або порожній файл loose-об'єкта (без копії поруч) | порожній файл переміщується до резервної копії, а об'єкти завантажуються заново (`git fetch --refetch`, git 2.36 або новіший) з `--remote`, інакше з remote гілки, інакше з `origin`, інакше з єдиного remote; гілки й теги remote завантажуються в тимчасовий простір імен `refs/gcd-fetch/`, який потім видаляється, тож жоден ref не змінюється. Якщо remote не повернув об'єкт, виправлення відкочується |
| з `fix --deep`: об'єкти, про пошкодження яких повідомив `git fsck` | кожен об'єкт гілок і тегів remote завантажується заново тим самим способом; потім `git fsck` запускається знову, і якщо він досі повідомляє про помилки (об'єкт, якого немає на жодному remote, залишений пошкоджений файл), виправлення відкочується |
| конфліктні копії ваших власних файлів (`notes 2.md`), які git не відстежує і які побайтово збігаються з файлом, з якого скопійовані | переміщуються до резервної копії (`git add -A` закомітив би їх); копія, що відрізняється, відстежується, є посиланням, є лише в хмарі або розташована в підмодулі, залишається |
| `gc.pid` іншої машини, старший за годину; `gc.log` | переміщуються до резервної копії, щоб автоматичний gc git знову працював тут |
| файли `.git` або альтернативного сховища об'єктів, що є лише в хмарі | завантажуються, і більше нічого: до того перевірка не може читати об'єкти, тож решта пошкоджень перелічується як MANUAL до наступного запуску `fix` |

Усе інше перелічується як MANUAL разом із командою, яку треба виконати. Сюди входить усе, що може містити роботу, якої більше ніде немає:
- пошкоджений index (git, можливо, ще зможе прочитати його разом із підготовленою роботою);
- копія index або `index.lock`, що відрізняється від HEAD, а також копія `index.lock`;
- копія, у якої немає оригіналу (вона може бути єдиною: поверніть її на місце; якщо це копія блокування, її зберігають і відкладають убік);
- блокування, яке не утримує жоден git на цій машині (його може утримувати git на іншому пристрої чи в контейнері; порада називає коміт усередині);
- копія, що вказує понад 100 об'єктів (довгий reflog);
- копія гілки, на яку вказує будь-який HEAD, її reflog або каталогу, що її містить (git читає її, хай як виглядає ім'я).

А також усе, де fix мусив би обирати між двома версіями або не може зберегти коміти копії:
- усе в сховищі об'єктів: копії, файли з іменем об'єкта (перевірте, який збігається зі своїм хешем), порожні файли об'єктів без remote для завантаження;
- усе в каталозі git підмодуля (запустіть `fix` у підмодулі);
- копія гілки, що вказує на коміт, якого тут ще немає (він може ще прийти);
- копія `.git` у робочому дереві з комітами, яких немає в репозиторії (ви вирішуєте, яка з них актуальна);
- порожній файл, поруч із яким лежить копія його самого або його каталогу;
- пошкоджений службовий каталог пов'язаного робочого дерева (`git worktree repair`);
- index, що втратив файли, які ще є на диску (навмисне припинення відстеження виглядає так само; якщо більше нічого не підготовлено, порада каже, що `git read-tree HEAD` поверне їх без втрат);
- без `--deep` або без remote — об'єкти, про пошкодження яких повідомив `git fsck`.

`fix` узагалі не чіпає репозиторії reftable; там знахідка `REFTABLE_TABLE_UNLISTED` від `check` підкаже, як зберегти refs іншого пристрою. Резервна копія має бути на диску репозиторію, щоб те, що fix відкладає вбік, переміщувалося за один крок; інакше `fix` відмовляє (виправлення, що полягає лише в завантаженні, нічого не переміщує і цього не потребує).

Кожен крок записується до виконання, а наприкінці перевірка запускається знову: якщо виправлене досі виявляється або з'явилося нове пошкодження, кроки скасовуються. Перерваний fix відкочується наступною змінювальною командою, запущеною з `--apply` у цьому репозиторії; після цього вона зупиняється — запустіть її знову. Через 30 секунд (`--watch`) `fix` перевіряє ще раз: пошкодження, що повернулося, приніс клієнт синхронізації, і довготривале рішення — `move-out`.

`undo` скасовує спершу найновішу зміну — виправлення або перенесення. Крок, результат якого змінився після виправлення, залишається як є і вказується в переліку, але ніколи не перезаписується: git переписав перестворений index, клієнт синхронізації повернув копію, rescue-ref зсунувся, резервну копію видалено або `.git` перенесено. Rescue-ref залишається, поки копія, яку він зберігає, лежить у резервній копії. Завантажені файли залишаються на диску, а повторно завантажені об'єкти — у сховищі об'єктів: ні те, ні інше нічого не замінює. Решта скасовується, і undo завершується, тож потім можна скасувати попередню зміну.

`history` перелічує зміни, які цей пристрій вніс у репозиторій (виправлення, перенесення, скасування), резервну копію кожної з її розміром і те, яку зміну `undo` скасує наступною. `prune-backups`, лише з `--apply`, видаляє резервні копії змін, які було скасовано, відкочено або які від початку не можна скасувати (undo, prepare, attach) і чий останній крок старший за `--older-than` (за замовчуванням `720h`). Виправлення чи перенесення, яке ще можна скасувати, зберігає свою резервну копію, навіть якщо над ним є новіші зміни.

<a name="moving-git-out-of-the-synced-folder"></a>

## Перенесення .git за межі синхронізованої теки

```sh
gitbrella move-out            # що станеться і що може завадити
gitbrella move-out --apply    # виконати
gitbrella undo --apply        # повернути назад
```

<p align="center">
  <img src="../../assets/move-out.svg" width="860" alt="До: .git усередині синхронізованої теки. Після move-out: файл .git у синхронізованій теці вказує на ~/.local/share/gitbrella/gitdirs/notes-1a2b3c4d ззовні">
</p>

`move-out` копіює `.git` до `~/.local/share/gitbrella/gitdirs/<name>` (на macOS — клон APFS, що не займає місця), пофайлово доводить, що копія ідентична, переміщує оригінал до резервної копії в `~/Library/Application Support/gitbrella` (Linux: `$XDG_STATE_HOME/gitbrella`) і записує файл `.git` на кшталт `gitdir: ../../../../.local/share/gitbrella/gitdirs/notes-1a2b3c4d`. Шлях відносний, тому кожен пристрій, де тека лежить у тому самому місці домашнього каталогу, записує однаковий файл `.git`. Потім перевіряється, що git знаходить той самий HEAD, статус, конфігурацію й каталог hooks, а протягом 30 секунд (`--watch`) — що клієнт синхронізації не чіпає `.git`, а в iCloud ще й вивантажує новий файл. Оригінал відкладається вбік до фінального порівняння, тож запис, що проскочив під час копіювання, буде виявлено, і перенесення буде скасовано. В iCloud `move-out` відмовляє, поки iCloud ще вивантажує репозиторій; `--wait-upload 10m` натомість чекає до вказаного часу.

Кожна зміна записується до журналу до виконання разом із пристроєм та inode всього, що вона створює (і байтами файлу `.git`); відкат не чіпає нічого іншого. Якщо процес переривається посередині, наступний `move-out --apply` (або `undo --apply`) завершує або відкочує його й зупиняється (запустіть команду знову, щоб продовжити); незавершену зміну знаходять за inode теки — навіть якщо шлях записано інакше, після перейменування чи всередині іншого репозиторію. Тим часом `check` повідомляє про незавершену зміну як про пошкодження. Ніщо не відкочується поверх перенесеного каталогу після того, як git почав його використовувати: якщо в ньому є щось, чого немає в оригіналі, команда зупиняється і називає обидва. Нічого не видаляється: оригінал залишається в резервній копії, доки ви його не видалите. `undo` повертає каталог git, який використовується зараз, разом із комітами, зробленими після перенесення; резервна копія до перенесення не зачіпається. Якщо клієнт синхронізації вивантажив файл `.git` (на цьому Mac лишилося тільки його ім'я), `undo` і відновлення попросять спершу завантажити його: читання спричинило б завантаження, а цей інструмент ніколи його не виконує.

Якщо під час відкату виявлено і оригінал (у резервній копії), і новий `.git` (створений вами чи клієнтом синхронізації після зупинки перенесення), жоден з них не перезаписується, і про це повідомляється: порівняйте їх, винесіть непотрібний `.git` за межі теки й знову запустіть команду.

Відмовляє (код 1, з причинами), поки з репозиторієм працює git або щось, що утримує блокування git, під час merge чи rebase, поки файли `.git` є лише в хмарі, поки iCloud ще вивантажує теку, поки в `.git` є сокет (запущений `git fsmonitor--daemon`), коли після перенесення існують два каталоги git, а також для конфігурацій, у яких зламалися б зв'язки: пов'язані робочі дерева, підмодулі, запозичені об'єкти (`alternates`), `.git`, що є симлінком або не є самим каталогом git. Інші пошкодження, знайдені `check`, переносяться як є і перелічуються як перенесені: після цього запустіть `check` знову.

### Інші пристрої

Клієнт синхронізації видаляє `.git` на всіх інших пристроях, що синхронізують теку, і доставляє туди файл `.git`. Щоб зберегти їхню історію:

<p align="center">
  <img src="../../assets/other-devices.svg" width="820" alt="1: move-out --prepare --apply на кожному іншому пристрої. 2: move-out --apply на одному пристрої. 3: move-out --attach --apply на кожному іншому пристрої">
</p>

1. На кожному іншому пристрої, до перенесення: `gitbrella move-out --prepare --apply` копіює `.git` цього пристрою туди, куди вказуватиме файл `.git`.
2. На одному пристрої: `gitbrella move-out --apply`.
3. На кожному іншому пристрої, після того як надійшов файл `.git`: `gitbrella move-out --attach --apply`. Непідготовлений пристрій натомість клонує історію: `--attach --from <remote URL> --apply`. В обох випадках робоче дерево не зачіпається.

Файл `.git` надходить через клієнт синхронізації, тому attach довіряє йому лише настільки, наскільки дозволяють записи цього пристрою: він має вказувати всередину `~/.local/share/gitbrella/gitdirs` цього пристрою, а наявний там каталог використовується, лише якщо його створив `--prepare` для цього репозиторію.

Відтепер клієнт синхронізації переносить файли, а не історію. Діліться комітами через remote. На пристрої, де клієнт синхронізації вже оновив файли, `git pull` відмовить («would be overwritten»): використовуйте `git fetch` і `git reset --mixed @{u}`, що перемістить гілку й index, залишивши синхронізовані файли як є.

| `INDEX_COPY` | конфліктна копія index (`index 2`; імена Dropbox, Syncthing, Nextcloud/ownCloud, Proton Drive і Seafile; `index (1)` з Google Drive, `index-COMPUTER` з OneDrive у теці OneDrive, а також імена старого Nextcloud, Synology Drive, pCloud і Resilio зіставляються лише з власними іменами файлів git); указує, чи це коректний index і чи збігається він із HEAD |
| `REF_COPY` | конфліктна копія ref гілки або тегу; указує, чи копія старша, новіша, розійшлася або вказує на відсутній коміт |
| `COPY_IN_GITDIR` | будь-яка інша конфліктна копія в `.git` |
| `INDEX_MISSING` | index відсутній; git показує кожен файл видаленим (у хуку коміту: коміт видалив би всі файли) |
| `INDEX_EMPTY` | index не перелічує жодного файлу, хоча файли HEAD ще в робочому дереві, — так буває, коли git перестворив index після того, як клієнт синхронізації його видалив; коміт видалив би всі файли |
| `INDEX_SHRUNK` | index більше не перелічує файли HEAD, які ще в робочому дереві (у sparse checkout: будь-який файл HEAD), — так буває, коли git перестворив його з підготовлених файлів після того, як клієнт синхронізації видалив index; коміт видалив би їх. Перейменування, каталог, що став симлінком або підмодулем, оголошеним у `.gitmodules`, і файли, видалені й з диска, не враховуються; якщо файли HEAD не вдається перелічити, повідомляється як неперевірене |
| `HEAD_COMMIT_MISSING` | HEAD вказує на коміт, якого немає в репозиторії (ref прийшов раніше за свої об'єкти) |
| `ORPHAN_INDEX_LOCK` | index відсутній, а старий `index.lock` залишився (часто це повний index) |
| `INDEX_INVALID` | index не проходить власну контрольну суму |
| `STALE_LOCK` | блокування git, яке не може утримувати жоден запущений git: із репозиторієм не працює жоден або всі запущені після запису блокування. Видно лише процеси git на цій машині: перш ніж видаляти блокування, переконайтеся, що жоден git не використовує репозиторій у контейнері, на іншій машині, яка поділяє теку, або в застосунку з вбудованим git |
| `DATALESS_IN_GITDIR` | файли в `.git` є лише в хмарі; перевірки об'єктів пропущено |
| `FOREIGN_FILE_IN_GITDIR` | файл у `refs/` або `objects/`, створений не git (`desktop.ini`, файли `.tmp` в `objects/`) |
| `EMPTY_FILE_IN_GITDIR` | об'єкт або ref нульового розміру |
| `GITDIR_COPY` | копія каталогу git у робочому дереві (`.git 2`) |
| `GIT_DIR_NOT_IGNORED` | каталог git лежить у робочому дереві під іншим ім'ям (`.git.nosync`), і `git add -A` закомітив би його |
| `WORKTREE_ADMIN_BROKEN` | пов'язане робоче дерево втратило свої службові файли |
| `STALE_OPERATION_STATE` | залишений каталог rebase змушує git думати, що триває rebase |
| `FSCK_ERRORS` | лише `--deep`: `git fsck` повідомив про помилки (якщо він не завершився, той самий код стає інформаційним) |
| `REFTABLE_TABLE_UNLISTED` | у репозиторії reftable є таблиці ref, не названі в його списку: таблиці іншого пристрою, принесені клієнтом синхронізації, чий список став копією, яку git ніколи не читає. Наступний `git pack-refs` або обслуговування видалить їх, а разом із ними й гілки того пристрою; спершу скопіюйте каталог git у безпечне місце |
| `CHANGE_UNFINISHED` | `fix`, `undo` або `move-out` gitbrella не завершився (його перервано); перш ніж використовувати там git, запустіть названу команду з `--apply`, щоб завершити або відкотити його |
| `GIT_DIR_RETURNED` | після `move-out` `.git` знову став каталогом (клієнт синхронізації повернув старий), тож існують два каталоги git; порівняйте їх і залиште один, перш ніж комітити |
| `STAGED_CONFLICT_COPY` | index додає конфліктну копію синхронізації файлу, який він також перелічує (`notes 2.md` поруч із `notes.md`, скопійований каталог `src 2/`, імена Syncthing); коміт вніс би копію в історію. Вирішують лише імена; перейменування на таке ім'я і файл з іменем копії без оригіналу не враховуються; за розділеного index не перевіряється |

Інформаційні (код виходу не змінюється): `IN_CLOUD_FOLDER`, `GIT_DIR_NOT_SYNCED` (каталог git винесено з синхронізованої теки: безпечна конфігурація), `WORKTREE_COPIES` (конфліктні копії ваших власних файлів), `GIT_RUNNING`, `LOCK_IN_USE`, `LOCK_RECENT`, `IN_PROGRESS_OPERATION`, `UNKNOWN_IN_GITDIR`, `NO_CHECKOUT`, `PARTIAL_CLONE_UNVERIFIED`, `WORKTREE_SCAN_TRUNCATED`, `DEEP_CHECK_SKIPPED`, `REFTABLE_UNSUPPORTED`, `UNREADABLE_IN_GITDIR`, `PROCESS_CHECK_FAILED`, `GIT_DIR_IGNORE_UNCHECKED`, `GIT_TEMP_FILE`, `DATALESS_IN_ALTERNATE` (в альтернативному сховищі об'єктів є файли лише в хмарі, тому перевірки об'єктів пропущено), `GC_PID_FOREIGN` (`gc.pid` іншої машини: git пропускає автоматичний gc на 12 годин), `GC_LOG_FRESH` (`gc.log`, молодший за добу, зупиняє автоматичний gc), `HOOKS_IN_SYNCED_FOLDER` (команда `core.hooksPath` або `core.fsmonitor` лежить у синхронізованій теці поза каталогом git, тому зміна на іншому пристрої виконується тут), `WORKTREE_GUESSED` (`GIT_DIR` без робочого дерева, а в поточному каталозі немає жодного файлу HEAD: робоче дерево не перевірялося).

Якщо шлях узагалі не є репозиторієм, повідомляється чому, коли причина на диску: перейменований `.git 2`, власні файли git лише в хмарі, каталог git без HEAD, файл `.git`, що вказує на каталог git, якого більше немає, або `core.worktree`, що вказує на теку, якої немає на цій машині (налаштування іншої машини, принесене клієнтом синхронізації). Якщо на шляху є `.git`, який git не може використати, перевірка зупиняється там (код 2), а не відповідає за зовнішній репозиторій, як зробив би сам git.

<a name="install"></a>

## Встановлення

Потрібен git 2.31 або новіший. macOS і Linux, amd64 і arm64, без cgo.

```
brew install aliyilmazco/tap/gitbrella
```

```
go install github.com/aliyilmazco/gitbrella/cmd/gitbrella@latest
```

або завантажте архів зі сторінки releases.

### Перевірка релізу

Кожен реліз містить `checksums.txt` (SHA-256 кожного архіву та SBOM), безключовий підпис cosign `checksums.txt.sigstore.json`, створений workflow релізу, SPDX SBOM для кожного архіву та атестацію походження збірки GitHub (build-provenance attestation). Спершу перевірте підпис, потім архів за підписаним списком (приклад — v1.2.3 для Apple silicon). Використовуйте cosign v3.1.3 або новіший (v2.6.5 у лінійці v2): старі версії можна обдурити підробленим бандлом (GHSA-fx35-mq7g-6g98).

```sh
cosign verify-blob \
  --certificate-identity 'https://github.com/aliyilmazco/gitbrella/.github/workflows/release.yml@refs/tags/v1.2.3' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  --bundle checksums.txt.sigstore.json checksums.txt
grep ' gitbrella_1.2.3_darwin_arm64.tar.gz$' checksums.txt | shasum -a 256 -c
gh attestation verify gitbrella_1.2.3_darwin_arm64.tar.gz \
  --repo aliyilmazco/gitbrella \
  --signer-workflow aliyilmazco/gitbrella/.github/workflows/release.yml \
  --source-ref refs/tags/v1.2.3 --deny-self-hosted-runners
```

Реліз збирається з надісланого тегу workflow `.github/workflows/release.yml` за допомогою `.goreleaser.yaml` і залишається чернеткою, доки його не опублікує людина. Бінарники збираються з `-trimpath` і часом коміту, тому той самий тег і той самий реліз Go (workflow бере останній патч 1.26) дають однакові бінарники; архіви та SBOM навколо них містять час збирання.

<a name="limits"></a>

## Обмеження

- `fix` виправляє лише там, де є одна правильна відповідь, а решту залишає вам із командою для виконання; довготривале рішення — `move-out`, який тримає `.git` поза синхронізованою текою.
- Конфліктні копії, які сам iCloud створює між двома пристроями, у тестах не відтворювалися; виявлення перевірено на копіях із тим самим іменуванням.
- Codex не передає хукам `workdir` свого інструмента оболонки: команда, яку Codex виконує в іншій теці, перевіряється в теці сесії.
- Windows та OneDrive у Windows не тестувалися. Для репозиторіїв reftable виконуються перевірки на рівні файлів і перевірка неперелічених таблиць; копії ref там не порівнюються зі своїми гілками.
- Імена копій з позначками, які ім'я може містити навмисно, зіставляються лише там, де ім'я створює сам git, і ніколи в робочому дереві: `index (1)` з Google Drive — для власних файлів git і в `refs/`; `index-COMPUTER` з OneDrive — для власних файлів git на верхньому рівні теки OneDrive, з іменем пристрою, що містить велику літеру, не є словом, яким зазвичай закінчують ім'я резервної копії (`index-old`, `config-OLD`, `config-Backup`, `index-BAK` — ваші), і має не більше 15 символів (довше ім'я Mac буде пропущено); `_conflict-YYYYMMDD-HHMMSS` старого Nextcloud, імена Synology Drive, `.conflicted` pCloud і `.Conflict` Resilio — для власних файлів git на верхньому рівні (імена старого Nextcloud також у `refs/` і `logs/` поруч з оригіналом у теці Nextcloud). Гілка, на яку вказує будь-який HEAD (як `ref:` з будь-якими пробілами або як симлінк), її reflog і каталоги, що її містять, ніколи не відкладаються вбік, хай як вони називаються. Тому `report (1).pdf`, гілка `fix.Conflict`, тег `v1.0.conflicted` чи `config-backup` — звичайні імена.
- Підмодулі перевіряються зсередини підмодуля. З батьківського проєкту конфліктна копія в `.git/modules/<name>/` виявляється, лише якщо поруч лежить оригінал, а підмодуль з іменем копії (`lib 2`) повідомляється як копія.
- Відсутній index пов'язаного робочого дерева виявляється під час перевірки цього робочого дерева, а не основного.
- Якщо `.git` — симлінк на сховище поза синхронізованою текою, запускайте git і перевірку з пов'язаного робочого дерева. З каталогу сховища, де немає жодного файлу, спорожнілий index виглядає як навмисне «видалити все» і не блокує коміт.
- Деяким навмисним комітам потрібен `--no-verify`: припинення відстеження файлів, що залишаються на диску, видалення всіх файлів там, де не можна читати об'єкти, перейменування, що змінює лише регістр або форму Unicode файлу з іншим жорстким посиланням, а також будь-який коміт у sparse checkout (у режимі cone чи без нього), який видаляє чи перейменовує відстежуваний файл або переміщує його через зміну типу (файл, що став каталогом, каталог, що став симлінком чи підмодулем). Там шаблони sparse git вирішують, які файли є на диску, тож навмисне видалення неможливо відрізнити від втраченого index; шаблони не читаються.
- Якщо клієнт синхронізації разом з index втратив і сам ref гілки (його loose-файл видалено раніше, ніж прийшов новий `packed-refs`), HEAD виглядає як нова гілка, і коміт не блокується: він починає нову історію лише з підготовленими файлами. Нічого на диску не видаляється, а стара історія залишається в reflog (`git reflog`).
- За розділеного index або там, де не можна читати об'єкти (частковий клон із git, старішим за 2.45, альтернативні сховища лише в хмарі), index не порівнюється з HEAD пофайлово: виявляються лише відсутній або порожній index.
- З `core.splitIndex` index, що не перелічує жодного файлу, не розпізнається (його заголовок враховує лише розділену частину), тому коміт із нього не блокується.
- Хуки: лише хуки коміту знаходяться за процесом git, який їх запускає. Інші хуки (`pre-push`, `pre-applypatch`) мають запускати перевірку з робочого дерева, інакше отримують відмову (код 2). Там, де процес git не видно (клієнт, що сам запускає хуки, або заблокований перегляд процесів), перевірка використовує поточний каталог: тоді, якщо каталог git не вказує назад на робоче дерево (`--separate-git-dir`, `.git.nosync`, `--work-tree`), index без файлів завжди блокує коміт (для навмисного спорожнення використовуйте `--no-verify`), поточний каталог, що не містить жодного файлу HEAD, не перевіряється як робоче дерево (`WORKTREE_GUESSED`), а хук, що перейшов до іншого репозиторію чи каталогу git, отримує відмову (код 2). Хуки приймання (`pre-receive`) не є підтримуваним рубежем.
- `move-out`: файл `.git` розуміють не всі інструменти. Git та інструменти, що запускають git, працюють; isomorphic-git (Obsidian Git на мобільних) та інструменти, що відкривають `.git` як каталог, — ні.
- `move-out`: перейменування або переміщення синхронізованої теки ламає відносний файл `.git`. Тоді `check` назве відсутній каталог; поверніть теку на місце або вручну спрямуйте файл `.git` на каталог git.
- `move-out` вимагає, щоб синхронізована тека була в тому самому місці домашнього каталогу на кожному пристрої (iCloud Drive — завжди; Dropbox може бути `~/Dropbox` на одному пристрої і `~/Library/CloudStorage/Dropbox` на іншому). Якщо це не так, файл `.git` там указує деінде, і `--attach` відмовляє (`TARGET_UNEXPECTED`).
- Перенесений каталог git розташований на файловій системі домашнього каталогу; опції розмістити його деінде немає.
- `move-out --prepare` копіює історію пристрою на той момент: переносьте невдовзі після підготовки, без нових комітів у проміжку.
- `move-out` і `fix` випробувано у власній теці iCloud Drive, а не в iCloud-теці застосунку (`iCloud~md~obsidian` в Obsidian).
