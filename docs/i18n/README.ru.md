iCloud Drive, Dropbox, OneDrive, Google Drive и Syncthing синхронизируют файлы по одному. Git же рассчитывает, что каталог `.git` меняется как единое целое, поэтому в репозитории внутри синхронизируемой папки появляются конфликтные копии вроде `.git/index 2` и `refs/heads/main 2`, пропавший index рядом с забытым `index.lock` и объекты, которые есть только в облаке. FAQ самого git предостерегает от хранения репозиториев в синхронизируемых папках, но настройки по умолчанию продолжают их туда класть: «Рабочий стол» и «Документы» в iCloud на macOS, резервное копирование папок в OneDrive на Windows, `Documents/GitHub`.

<p align="center">
  <img src="../../assets/sync-damage.svg" width="820" alt="Клиент синхронизации копирует .git между устройствами файл за файлом и оставляет конфликтные копии вроде index 2 и refs/heads/main 2, index.lock рядом с пропавшим index и объекты, которые есть только в облаке">
</p>

`gitbrella check` обычно меньше чем за секунду сообщает, есть ли в репозитории такие повреждения. Он рассчитан на запуск до того, как к репозиторию прикоснётся ИИ-агент или git-хук. `gitbrella fix` исправляет то, у чего есть ровно один правильный способ восстановления, а `gitbrella move-out` устраняет повреждения в корне: переносит `.git` из синхронизируемой папки и оставляет на его месте файл `.git`, указывающий туда, так что клиент синхронизации переносит ваши файлы, а git держит историю при себе.

| Команда | Что делает |
| --- | --- |
| `gitbrella check` | сообщает о повреждениях (только чтение) |
| `gitbrella fix` | исправляет то, у чего один правильный ответ |
| `gitbrella move-out` | навсегда выносит `.git` из синхронизируемой папки |
| `gitbrella undo` | отменяет последнее исправление или перенос |
| `gitbrella history` | список изменений, сделанных на этом устройстве |
| `gitbrella prune-backups` | удаляет старые резервные копии изменений, которые уже нельзя отменить |
| `gitbrella hook --for claude\|codex` | защищает вызовы инструментов ИИ-агента |

## Быстрый старт

**1. Проверить.** Только чтение, без скачивания и без сети.

```sh
cd ~/Library/Mobile\ Documents/com~apple~CloudDocs/notes
gitbrella check               # код 0: в порядке, 1: повреждения, 2: не удалось запустить
```

**2. Исправить.** Только то, у чего один правильный ответ. Без `--apply` лишь показывает план.

```sh
gitbrella fix                 # что будет исправлено и что останется вам
gitbrella fix --apply         # исправить; `gitbrella undo --apply` вернёт как было
```

**3. Решить навсегда.** Вынести `.git` из синхронизируемой папки.

```sh
gitbrella move-out            # что произойдёт и что может помешать
gitbrella move-out --apply
```

**Оставаться под защитой.** Блокировать коммиты в повреждённом репозитории:

```sh
printf '#!/bin/sh\nexec gitbrella check\n' > .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit
```

Для ИИ-агентов см. [Для агентов](#for-agents).

## Что гарантируется

- <img src="../../assets/icons/read-only.svg" width="18" alt=""> **`check` только читает.** Он никогда не пишет в репозиторий. Git запускает только читающие команды, с `GIT_OPTIONAL_LOCKS=0` и отключёнными автоматическим gc и обслуживанием. Сквозные тесты для рискованных случаев (копия index, пропавший index, частичный клон, разделённый index, перенесённый каталог git) записывают размер, mtime и inode каждого файла до и после проверки и сравнивают их.
- <img src="../../assets/icons/no-download.svg" width="18" alt=""> **Ничего не скачивает из облака.** На macOS он отключает загрузку по требованию для своего процесса (и запускаемого им git) до того, как прикоснуться к диску; если macOS отказывает, проверка не запускается (код 2). Файл, который есть только в iCloud, попадает в отчёт, но не загружается.
- <img src="../../assets/icons/no-network.svg" width="18" alt=""> **Не обращается к сети.** Частичный клон никогда не догружает отсутствующие объекты (`GIT_NO_LAZY_FETCH`); с git старше 2.45 проверки объектов вместо этого пропускаются.
- <img src="../../assets/icons/quiet.svg" width="18" alt=""> **Молчит на здоровых репозиториях.** Блокировка считается повреждением, только если она старая и ни один git, работающий с этим репозиторием (с любым его рабочим деревом), не мог её записать: git создаёт блокировку, когда берёт её, так что git, запущенный позже, не может её удерживать. Временные файлы git и файлы других инструментов внутри `.git` — информационные. Запуск на 89 здоровых репозиториях, находящихся в работе, не выявил ни одного повреждения.

## Использование

```
gitbrella check [--json] [--deep] [--provider NAME] [path]
```

Коды выхода: **0** повреждений нет, **1** найдены повреждения, **2** проверку не удалось выполнить. Для команд, которые что-то меняют (`move-out`, `fix`, `undo`): **0** запланировано, выполнено или делать нечего (`already`), **1** отказ (с причинами), выполнено с предупреждениями или остались повреждения, оставленные вам (список MANUAL у `fix`; `check` продолжает о них сообщать), **2** сбой (откат или остановка; JSON сохраняет то, что удалось восстановить, и записи журнала) или не удалось запустить.

`--deep` дополнительно запускает полный `git fsck` (он читает все объекты, поэтому пропускается, если объекты есть только в облаке). `--provider` задаёт клиент синхронизации вместо определения по пути: `auto` (по умолчанию), `icloud`, `icloud-desktop-documents`, `dropbox`, `onedrive`, `google-drive`, `syncthing`, `nextcloud`, `cloud-storage`, `none`. Папки Syncthing и Nextcloud (или ownCloud) распознаются в любом месте по маркеру, который клиент кладёт внутрь (`.stfolder`, `.sync_*.db`). `fix` и `move-out` принимают тот же `--provider`; передайте то же значение, что и `check`, потому что некоторые имена копий учитываются только для определённого клиента. В JSON тогда будет `"providerForced": true`.

### Как git-хук

```sh
#!/bin/sh
# .git/hooks/pre-commit
exec gitbrella check
```

<p align="center">
  <img src="../../assets/hook-flow.svg" width="820" alt="git commit запускает хук pre-commit, который запускает gitbrella check: при коде 0 коммит проходит, при 1 или 2 он блокируется">
</p>

В повреждённом репозитории коммит блокируется, в здоровом проходит как обычно. Инструмент знает, что хук запустил git, и не принимает собственную блокировку коммита за старую.

**Какой репозиторий проверяется.** В хуках коммита (git передаёт им `GIT_INDEX_FILE` или абсолютный `GIT_DIR`) репозиторий находится по процессу git, запустившему хук, поэтому хук может сначала сменить каталог: на каталог git, его каталог hooks или каталог вне всякого репозитория. Если git указывает репозиторий через абсолютный `GIT_DIR` (связанное рабочее дерево, подмодуль, отделённый каталог git), каждая команда git в хуке работает с ним, куда бы хук ни перешёл, и проверка тоже. В остальных случаях проверяется, куда ведёт текущий каталог для самого git (каталог git, на который там указывает относительный `GIT_DIR`, или репозиторий, найденный оттуда); если это другой репозиторий или другое рабочее дерево того же репозитория (хук, который туда переходит, или редактор сообщения коммита), проверка отказывается (код 2), а не отвечает за чужой репозиторий.

Без пути проверяется репозиторий, который git экспортировал хуку (`GIT_DIR`), поэтому работают и dotfiles-конфигурации с `--git-dir`, и каталог git внутри собственного рабочего дерева. Без пути учитывается и `GIT_DIR`, заданный в оболочке; в отличие от git, несуществующий `GIT_DIR` игнорируется, а связанное рабочее дерево, по которому нельзя пройти, отвергается вместо того, чтобы считать рабочим деревом текущий каталог.

**Index, который записывает коммит.** Если `GIT_INDEX_FILE` указывает на файл внутри каталога git (так git делает для хуков коммита), читается он. Если index, который запишет коммит, отсутствует или пуст, либо больше не перечисляет файлы HEAD, ещё лежащие в рабочем дереве, коммит блокируется до того, как он запишет их удаление. Файл index в другом месте, указанный вами через `GIT_INDEX_FILE`, не читается: внутри хука вместо него проверяется собственный index репозитория, а ручная проверка с этой переменной отвергается (код 2).

**Намеренные удаления.** Чтобы перестать отслеживать файлы, которые останутся на диске (`git rm --cached`, прекращение отслеживания каталога, который теперь игнорируется), или намеренно закоммитить «удалить всё», пока файлы ещё на диске (`git rm -r --cached .`), пропустите хук с помощью `git commit --no-verify`.

### С менеджером хуков

- **pre-commit** (pre-commit.com): добавьте этот репозиторий с id хука `gitbrella` (pre-commit соберёт его на Go) или `gitbrella-system` (бинарник из PATH); см. `.pre-commit-hooks.yaml`.
- **lefthook**: подключите `hooks/lefthook.yml` через `remotes`.
- **husky**: `.husky/pre-commit`, содержащий `gitbrella check`.
- **Overcommit**: `PreCommit: { Gitbrella: { enabled: true, required_executable: gitbrella, command: [gitbrella, check] } }`, затем `overcommit --sign`.

Во всех них любой ненулевой код останавливает коммит, так что проверка, которая не смогла запуститься (код 2), тоже его останавливает. Aider коммитит с `--no-verify`, если не задано `git-commit-verify: true`, и тогда ни один хук коммита не запускается. Obsidian Git (десктоп) коммитит системным git и запускает хук; добавьте папку с `gitbrella` в его настройку «Additional PATH», так как приложения, запущенные из Dock, не получают PATH оболочки. Obsidian Git на мобильных устройствах (isomorphic-git) хуки не запускает.

<a name="for-agents"></a>

### Для агентов

`--json` выводит тот же отчёт как стабильный версионированный документ (`schemaVersion: 1`, `findings` всегда список). Решайте по коду выхода и показывайте найденное пользователю.

Собственные хуки агентов останавливают вызов инструмента только при коде 2: код 1 («найдены повреждения») пропускает вызов. `gitbrella hook --for claude|codex` говорит на языке их хуков. Он читает событие, которое агент передаёт через stdin:

<p align="center">
  <img src="../../assets/agent-hook.svg" width="820" alt="Вызов инструмента агентом проходит через gitbrella hook: чтение и редактирование продолжаются; в повреждённом репозитории запись через git и запись в .git останавливаются кодом 2">
</p>

- **Перед вызовом инструмента** (`PreToolUse`): в повреждённом репозитории пишущая команда git (commit, add, reset, rebase, push и всё, о чём не известно, что оно только читает) и запись в `.git` останавливают вызов (код 2, причина для агента в stderr). Чтение, редактирование ваших файлов, `git restore` и сам `gitbrella` продолжаются, чтобы повреждение можно было осмотреть и исправить.
  - *Непригодные репозитории.* Там, где файлы git есть только в облаке или git вообще не может использовать репозиторий (переименованный `HEAD`, файл `.git`, указывающий в никуда), останавливается каждая команда git: она бы зависла или подействовала на внешний репозиторий. Запись в `.git` там продолжается: такое исправление делается вручную внутри `.git`, как сказано в причине (`mv '.git/HEAD 2' .git/HEAD`). Средство, названное в подсказке `core.worktree` (`git config --file … --unset core.worktree`), тоже продолжается.
  - *Какой репозиторий.* Тот, что содержит файлы, с которыми работает вызов (патч Codex называет свои файлы; путь внутри `.git` относится к рабочему дереву над ним). Для команды оболочки — папка сессии и каждая папка, в которой выполняются её команды git (`cd DIR`, `pushd`, `git -C DIR`, `--git-dir`, `--work-tree`, `GIT_DIR`, `env -C`, `bash -c '…'`), сначала пишущие, не более пяти; если пишущая не помещается, вызов проходит с предупреждением. Каждая папка оценивается по тому, что вызов в ней делает: `git -C ../sound commit` из повреждённой папки сессии продолжается. Папка, не являющаяся репозиторием, и bare-репозиторий проходят молча.
  - *Когда проверку не удаётся запустить.* Всё, что мешает проверке выполниться (включая 20-секундный `--timeout` — единый срок на весь вызов), пропускает вызов с предупреждением; `--fail-open` делает то же там, где git не может использовать репозиторий.
  - *Как читается команда.* Она читается, но никогда не выполняется: кавычки, комментарии, подоболочки, подстановки (в том числе внутри heredoc без кавычек), heredoc, переменные, которые она задаёт, `&&`, `||`, `if`, `case` и циклы (после `cd a || cd b` или `cd` в несуществующую папку учитывается каждая папка, где может оказаться оболочка; цикл `for` читается по разу для каждого значения), обёртки (`timeout`, `sudo`, `nice`, `xargs`, `env`) и скрипты, переданные оболочке (`-c`, `eval`, `watch`, `source`, файл, heredoc, `bash < f`, конвейер в `sh`). Функции и алиасы, определённые командой, читаются там, где вызываются. Скрипт оболочки, запущенный по пути или переданный оболочке (`./deploy.sh`, `bash deploy.sh`), читается, если это небольшой файл на этой машине (в том числе через симлинк; один раз, даже если он запускает сам себя); `make`, `npm run` и подобные не читаются.
  - *Что считается записью.* Запись другой программы в `.git` (`rm .git/index.lock`, `> .git/HEAD`, `cd .git && rm index.lock`, `sed -i` для `.git/config`, `rm -rf` или `find -delete` для папки, содержащей `.git`, патч Codex через оболочку) считается записью в `.git`; копирование `.git` в другое место, упаковка в `tar` или чтение — нет. `gh pr checkout` и `git-lfs` считаются пишущими командами git.
  - *В случае сомнений.* Каждое из следующего считается пишущей командой git: чтение дольше 5000 шагов или половины `--timeout` (в той папке, которую не удалось определить); слово `git` там, куда чтение не следует; скрипт, переданный по конвейеру в оболочку из программы, за которой чтение не следует (`curl … | sh`), там, где он выполняется; существующий, но нечитаемый скрипт, переданный оболочке (слишком большой, только в облаке), там, где он выполняется. Если не удаётся определить, в какую папку пишет команда git (`cd "$(…)"`, `for d in */`), она учитывается в каждой проверяемой папке, а вызов получает предупреждение.
- **В начале сессии** (`SessionStart`): одна строка в stdout, которую агент читает как контекст: что репозиторий находится в синхронизируемой папке (если его каталог git ещё не вынесен) и что повреждено. Никогда не блокирует.

Хук ничего не меняет. Для Claude Code в `.claude/settings.json`:

```json
{
  "hooks": {
    "SessionStart": [{"hooks": [{"type": "command", "command": "gitbrella hook --for claude"}]}],
    "PreToolUse": [{"matcher": "Edit|Write|MultiEdit|NotebookEdit|Bash",
                    "hooks": [{"type": "command", "command": "gitbrella hook --for claude"}]}]
  }
}
```

Для Codex в `.codex/hooks.json` (Codex запускает хук только после того, как вы доверите ему в `/hooks`):

```json
{
  "hooks": {
    "SessionStart": [{"hooks": [{"type": "command", "command": "gitbrella hook --for codex"}]}],
    "PreToolUse": [{"matcher": "Bash|apply_patch",
                    "hooks": [{"type": "command", "command": "gitbrella hook --for codex"}]}]
  }
}
```

Проверка выполняется по одному разу для каждой из этих папок, обычно по 0,1–0,4 секунды, поэтому патч, затрагивающий несколько папок одного репозитория, проверяет этот репозиторий несколько раз; `--timeout` ограничивает весь вызов.

<a name="repairing"></a>

## Восстановление

```sh
gitbrella fix                 # что будет исправлено и что останется вам
gitbrella fix --apply         # исправить
gitbrella undo --apply        # вернуть всё как было
gitbrella history             # изменения, сделанные здесь, их резервные копии и размеры
gitbrella prune-backups       # резервные копии, которые уже не нужны ни одному undo
```

<p align="center">
  <img src="../../assets/fix-flow.svg" width="820" alt="fix показывает план; fix --apply записывает каждый шаг, затем проверка запускается снова: готово или откат; undo --apply отменяет последнее изменение">
</p>

`check` указывает под каждым повреждением, исправит ли его `fix` (`repair:` и `"repair": "fix"` или `"manual"` в JSON), и называет `fix --provider NAME`, если проверке был задан провайдер. Внутри хуков коммита он ничего не спрашивает.

`fix` исправляет только там, где есть один правильный ответ и ничего, что вы могли иметь в виду, не перезаписывается:

| Повреждение | Исправление |
| --- | --- |
| конфликтные копии в `.git` рядом с оригиналом (`HEAD 2`, `refs/heads/main 2`, `refs 2`, `packed-refs 2`, копии Dropbox и Syncthing, а также копия блокировки ref, например `refs/heads/main 2.lock`); копия index — только если она идентична index или является корректным index, равным HEAD | перемещаются в резервную копию; объект (коммит, тег, дерево или файл), на который указывает только копия, сначала сохраняется как `refs/gcd-rescue/<name>` |
| оставшийся каталог rebase, `desktop.ini`, `Icon` и подобные файлы, созданные не git (если только git не читает их как ветку или их имя не является именем объекта), копия `.git` в рабочем дереве, коммиты которой уже есть в репозитории | перемещаются в резервную копию |
| отсутствующий index без копий и блокировок где бы то ни было | создаётся из HEAD (`git read-tree HEAD`: файлы не затрагиваются), только если есть коммит, на основе которого его строить (если коммит HEAD тоже отсутствует, он сначала догружается, как описано ниже), и вне sparse checkout |
| index, не перечисляющий ни одного файла (корректный, неразделённый index вне sparse checkout) | перемещается в резервную копию и создаётся из HEAD: в нём ничего не было подготовлено к коммиту |
| осиротевший `index.lock`, являющийся корректным index, равным HEAD | становится index |
| пустой файл ветки | коммит, который последним записал её reflog |
| `.git.nosync`, который git добавил бы в коммит | строка `/.git.nosync/` в `.git/info/exclude` |
| отсутствующий коммит HEAD или пустой файл loose-объекта (без копии рядом) | пустой файл перемещается в резервную копию, а объекты загружаются заново (`git fetch --refetch`, git 2.36 или новее) с `--remote`, иначе с remote ветки, иначе с `origin`, иначе с единственного remote; ветки и теги remote загружаются во временное пространство имён `refs/gcd-fetch/`, которое затем удаляется, так что ни один ref не меняется. Если remote не вернул объект, исправление откатывается |
| с `fix --deep`: объекты, о повреждении которых сообщил `git fsck` | каждый объект веток и тегов remote загружается заново тем же способом; затем `git fsck` запускается снова, и если он всё ещё сообщает об ошибках (объект, которого нет ни на одном remote, оставшийся повреждённый файл), исправление откатывается |
| конфликтные копии ваших собственных файлов (`notes 2.md`), которые git не отслеживает и которые побайтно совпадают с файлом, с которого скопированы | перемещаются в резервную копию (`git add -A` закоммитил бы их); копия, которая отличается, отслеживается, является ссылкой, есть только в облаке или находится в подмодуле, остаётся |
| `gc.pid` другой машины старше часа; `gc.log` | перемещаются в резервную копию, чтобы автоматический gc git снова работал здесь |
| файлы `.git` или альтернативного хранилища объектов, которые есть только в облаке | скачиваются, и больше ничего: до этого проверка не может читать объекты, поэтому остальные повреждения перечисляются как MANUAL до следующего запуска `fix` |

Всё остальное перечисляется как MANUAL вместе с командой, которую нужно выполнить. Сюда входит всё, что может содержать работу, которой больше нигде нет:
- повреждённый index (git, возможно, ещё сможет прочитать его вместе с подготовленной работой);
- копия index или `index.lock`, отличающаяся от HEAD, а также копия `index.lock`;
- копия, у которой нет оригинала (она может быть единственной: верните её на место; если это копия блокировки, она сохраняется и откладывается в сторону);
- блокировка, которую не удерживает ни один git на этой машине (её может удерживать git на другом устройстве или в контейнере; в совете назван коммит внутри неё);
- копия, указывающая более чем на 100 объектов (длинный reflog);
- копия ветки, на которую указывает какой-либо HEAD, её reflog или каталога, содержащего её (git читает её, как бы ни выглядело имя).

А также всё, где fix пришлось бы выбирать между двумя версиями или где он не может сохранить коммиты копии:
- всё в хранилище объектов: копии, файлы с именем объекта (проверьте, какой из них совпадает со своим хешем), пустые файлы объектов без remote для загрузки;
- всё в каталоге git подмодуля (запустите `fix` в подмодуле);
- копия ветки, указывающая на коммит, которого здесь ещё нет (он может ещё прийти);
- копия `.git` в рабочем дереве с коммитами, которых нет в репозитории (вы решаете, какая из них актуальна);
- пустой файл, рядом с которым лежит копия его самого или его каталога;
- повреждённый служебный каталог связанного рабочего дерева (`git worktree repair`);
- index, потерявший файлы, которые ещё есть на диске (намеренное прекращение отслеживания выглядит так же; если больше ничего не подготовлено, совет говорит, что `git read-tree HEAD` вернёт их без потерь);
- без `--deep` или без remote — объекты, о повреждении которых сообщил `git fsck`.

`fix` вообще не трогает репозитории reftable; там находка `REFTABLE_TABLE_UNLISTED` от `check` подскажет, как сохранить refs другого устройства. Резервная копия должна находиться на диске репозитория, чтобы то, что fix откладывает в сторону, перемещалось за один шаг; иначе `fix` отказывается (исправление, состоящее только из скачивания, ничего не перемещает и в этом не нуждается).

Каждый шаг записывается до выполнения, а в конце проверка запускается снова: если исправленное всё ещё обнаруживается или появилось новое повреждение, шаги отменяются. Прерванный fix откатывается следующей изменяющей командой, запущенной с `--apply` в этом репозитории; после этого она останавливается — запустите её снова. Через 30 секунд (`--watch`) `fix` проверяет ещё раз: вернувшееся повреждение принёс клиент синхронизации, и долгосрочное решение — `move-out`.

`undo` отменяет сначала самое новое изменение — исправление или перенос. Шаг, результат которого изменился после исправления, остаётся как есть и указывается в списке, но никогда не перезаписывается: git переписал пересозданный index, клиент синхронизации вернул копию, rescue-ref сдвинулся, резервная копия удалена или `.git` перенесён. Rescue-ref остаётся, пока копия, которую он сохраняет, лежит в резервной копии. Скачанные файлы остаются на диске, а загруженные заново объекты — в хранилище объектов: ни то, ни другое ничего не заменяет. Остальное отменяется, и undo завершается, так что затем можно отменить предыдущее изменение.

`history` перечисляет изменения, которые это устройство внесло в репозиторий (исправления, переносы, отмены), резервную копию каждого с её размером и то, какое изменение `undo` отменит следующим. `prune-backups`, только с `--apply`, удаляет резервные копии изменений, которые были отменены, откачены или изначально не отменяемы (undo, prepare, attach) и чей последний шаг старше `--older-than` (по умолчанию `720h`). Исправление или перенос, который ещё можно отменить, сохраняет свою резервную копию, даже если поверх есть более новые изменения.

<a name="moving-git-out-of-the-synced-folder"></a>

## Перенос .git из синхронизируемой папки

```sh
gitbrella move-out            # что произойдёт и что может помешать
gitbrella move-out --apply    # выполнить
gitbrella undo --apply        # вернуть обратно
```

<p align="center">
  <img src="../../assets/move-out.svg" width="860" alt="До: .git внутри синхронизируемой папки. После move-out: файл .git в синхронизируемой папке указывает на ~/.local/share/gitbrella/gitdirs/notes-1a2b3c4d снаружи">
</p>

`move-out` копирует `.git` в `~/.local/share/gitbrella/gitdirs/<name>` (на macOS — клон APFS, не занимающий места), пофайлово доказывает, что копия идентична, перемещает оригинал в резервную копию в `~/Library/Application Support/gitbrella` (Linux: `$XDG_STATE_HOME/gitbrella`) и записывает файл `.git` вида `gitdir: ../../../../.local/share/gitbrella/gitdirs/notes-1a2b3c4d`. Путь относительный, поэтому каждое устройство, где папка лежит в том же месте домашнего каталога, записывает одинаковый файл `.git`. Затем проверяется, что git находит тот же HEAD, статус, конфигурацию и каталог hooks, и в течение 30 секунд (`--watch`) — что клиент синхронизации не трогает `.git`, а в iCloud ещё и загружает новый файл. Оригинал откладывается в сторону до финального сравнения, поэтому запись, проскочившая во время копирования, будет обнаружена, и перенос будет отменён. В iCloud `move-out` отказывается, пока iCloud ещё выгружает репозиторий; `--wait-upload 10m` вместо этого ждёт до указанного времени.

Каждое изменение записывается в журнал до выполнения вместе с устройством и inode всего, что оно создаёт (и байтами файла `.git`); откат не трогает ничего другого. Если процесс прерывается посередине, следующий `move-out --apply` (или `undo --apply`) завершает или откатывает его и останавливается (запустите команду снова, чтобы продолжить); незавершённое изменение находится по inode папки — даже если путь записан иначе, после переименования или внутри другого репозитория. Тем временем `check` сообщает о незавершённом изменении как о повреждении. Ничто не откатывается поверх перенесённого каталога после того, как git начал его использовать: если в нём есть что-то, чего нет в оригинале, команда останавливается и называет оба. Ничего не удаляется: оригинал остаётся в резервной копии, пока вы его не удалите. `undo` возвращает каталог git, который используется сейчас, вместе с коммитами, сделанными после переноса; резервная копия до переноса не затрагивается. Если клиент синхронизации выгрузил файл `.git` (на этом Mac осталось только его имя), `undo` и восстановление попросят сначала скачать его: чтение вызвало бы загрузку, а этот инструмент её никогда не выполняет.

Если при откате обнаружены и оригинал (в резервной копии), и новый `.git` (созданный вами или клиентом синхронизации после остановки переноса), ни один из них не перезаписывается, и об этом сообщается: сравните их, вынесите ненужный `.git` из папки и снова запустите команду.

Отказывается (код 1, с причинами), пока с репозиторием работает git или что-то, удерживающее блокировку git, во время merge или rebase, пока файлы `.git` есть только в облаке, пока iCloud ещё выгружает папку, пока в `.git` есть сокет (работающий `git fsmonitor--daemon`), когда после переноса существуют два каталога git, а также для конфигураций, в которых сломались бы ссылки: связанные рабочие деревья, подмодули, заимствованные объекты (`alternates`), `.git`, являющийся симлинком или не являющийся самим каталогом git. Другие повреждения, найденные `check`, переносятся как есть и перечисляются как перенесённые: после этого запустите `check` снова.

### Другие устройства

Клиент синхронизации удаляет `.git` на всех остальных устройствах, синхронизирующих папку, и доставляет туда файл `.git`. Чтобы сохранить их историю:

<p align="center">
  <img src="../../assets/other-devices.svg" width="820" alt="1: move-out --prepare --apply на каждом другом устройстве. 2: move-out --apply на одном устройстве. 3: move-out --attach --apply на каждом другом устройстве">
</p>

1. На каждом другом устройстве, до переноса: `gitbrella move-out --prepare --apply` копирует `.git` этого устройства туда, куда будет указывать файл `.git`.
2. На одном устройстве: `gitbrella move-out --apply`.
3. На каждом другом устройстве, после того как пришёл файл `.git`: `gitbrella move-out --attach --apply`. Неподготовленное устройство вместо этого клонирует историю: `--attach --from <remote URL> --apply`. В обоих случаях рабочее дерево не затрагивается.

Файл `.git` приходит через клиент синхронизации, поэтому attach доверяет ему лишь настолько, насколько позволяют записи этого устройства: он должен указывать внутрь `~/.local/share/gitbrella/gitdirs` этого устройства, а уже существующий там каталог используется, только если его создал `--prepare` для этого репозитория.

С этого момента клиент синхронизации переносит файлы, но не историю. Делитесь коммитами через remote. На устройстве, где клиент синхронизации уже обновил файлы, `git pull` откажется («would be overwritten»): используйте `git fetch` и `git reset --mixed @{u}`, что переместит ветку и index, оставив синхронизированные файлы как есть.

## Что сообщает

Повреждения (код 1):

| Код | Значение |
| --- | --- |
| `INDEX_COPY` | конфликтная копия index (`index 2`; имена Dropbox, Syncthing, Nextcloud/ownCloud, Proton Drive и Seafile; `index (1)` из Google Drive, `index-COMPUTER` из OneDrive в папке OneDrive, а также имена старого Nextcloud, Synology Drive, pCloud и Resilio сопоставляются только с собственными именами файлов git); указывает, корректный ли это index и совпадает ли он с HEAD |
| `REF_COPY` | конфликтная копия ref ветки или тега; указывает, старше ли копия, новее, разошлась или указывает на отсутствующий коммит |
| `COPY_IN_GITDIR` | любая другая конфликтная копия в `.git` |
| `INDEX_MISSING` | index отсутствует; git показывает каждый файл удалённым (в хуке коммита: коммит удалил бы все файлы) |
| `INDEX_EMPTY` | index не перечисляет ни одного файла, хотя файлы HEAD ещё в рабочем дереве, — так бывает, когда git пересоздал index после того, как клиент синхронизации его удалил; коммит удалил бы все файлы |
| `INDEX_SHRUNK` | index больше не перечисляет файлы HEAD, которые ещё в рабочем дереве (в sparse checkout: любой файл HEAD), — так бывает, когда git пересоздал его из подготовленных файлов после того, как клиент синхронизации удалил index; коммит удалил бы их. Переименования, каталог, ставший симлинком или подмодулем, объявленным в `.gitmodules`, и файлы, удалённые и с диска, не учитываются; если файлы HEAD не удаётся перечислить, сообщается как непроверенное |
| `HEAD_COMMIT_MISSING` | HEAD указывает на коммит, которого нет в репозитории (ref пришёл раньше своих объектов) |
| `ORPHAN_INDEX_LOCK` | index отсутствует, а старый `index.lock` остался (часто это полный index) |
| `INDEX_INVALID` | index не проходит собственную контрольную сумму |
| `STALE_LOCK` | блокировка git, которую не может удерживать ни один работающий git: с репозиторием не работает ни один или все запущены после записи блокировки. Видны только процессы git на этой машине: прежде чем удалять блокировку, убедитесь, что никакой git не использует репозиторий в контейнере, на другой машине, разделяющей папку, или в приложении со встроенным git |
| `DATALESS_IN_GITDIR` | файлы в `.git` есть только в облаке; проверки объектов пропущены |
| `FOREIGN_FILE_IN_GITDIR` | файл в `refs/` или `objects/`, созданный не git (`desktop.ini`, файлы `.tmp` в `objects/`) |
| `EMPTY_FILE_IN_GITDIR` | объект или ref нулевого размера |
| `GITDIR_COPY` | копия каталога git в рабочем дереве (`.git 2`) |
| `GIT_DIR_NOT_IGNORED` | каталог git лежит в рабочем дереве под другим именем (`.git.nosync`), и `git add -A` закоммитил бы его |
| `WORKTREE_ADMIN_BROKEN` | связанное рабочее дерево потеряло свои служебные файлы |
| `STALE_OPERATION_STATE` | оставшийся каталог rebase заставляет git думать, что идёт rebase |
| `FSCK_ERRORS` | только `--deep`: `git fsck` сообщил об ошибках (если он не завершился, тот же код становится информационным) |
| `REFTABLE_TABLE_UNLISTED` | в репозитории reftable есть таблицы ref, не названные в его списке: таблицы другого устройства, принесённые клиентом синхронизации, чей список стал копией, которую git никогда не читает. Следующий `git pack-refs` или обслуживание удалит их, а вместе с ними и ветки того устройства; сначала скопируйте каталог git в безопасное место |
| `CHANGE_UNFINISHED` | `fix`, `undo` или `move-out` gitbrella не завершился (был прерван); прежде чем использовать там git, запустите названную команду с `--apply`, чтобы завершить или откатить его |
| `GIT_DIR_RETURNED` | после `move-out` `.git` снова стал каталогом (клиент синхронизации вернул старый), так что существуют два каталога git; сравните их и оставьте один, прежде чем коммитить |
| `STAGED_CONFLICT_COPY` | index добавляет конфликтную копию файла, который он также перечисляет (`notes 2.md` рядом с `notes.md`, скопированный каталог `src 2/`, имена Syncthing); коммит внёс бы копию в историю. Решают только имена; переименование в такое имя и файл с именем копии без оригинала не учитываются; при разделённом index не проверяется |

Информационные (код выхода не меняется): `IN_CLOUD_FOLDER`, `GIT_DIR_NOT_SYNCED` (каталог git вынесен из синхронизируемой папки: безопасная конфигурация), `WORKTREE_COPIES` (конфликтные копии ваших собственных файлов), `GIT_RUNNING`, `LOCK_IN_USE`, `LOCK_RECENT`, `IN_PROGRESS_OPERATION`, `UNKNOWN_IN_GITDIR`, `NO_CHECKOUT`, `PARTIAL_CLONE_UNVERIFIED`, `WORKTREE_SCAN_TRUNCATED`, `DEEP_CHECK_SKIPPED`, `REFTABLE_UNSUPPORTED`, `UNREADABLE_IN_GITDIR`, `PROCESS_CHECK_FAILED`, `GIT_DIR_IGNORE_UNCHECKED`, `GIT_TEMP_FILE`, `DATALESS_IN_ALTERNATE` (в альтернативном хранилище объектов есть файлы только в облаке, поэтому проверки объектов пропущены), `GC_PID_FOREIGN` (`gc.pid` другой машины: git пропускает автоматический gc на 12 часов), `GC_LOG_FRESH` (`gc.log` моложе суток останавливает автоматический gc), `HOOKS_IN_SYNCED_FOLDER` (команда `core.hooksPath` или `core.fsmonitor` лежит в синхронизируемой папке вне каталога git, поэтому изменение на другом устройстве выполняется здесь), `WORKTREE_GUESSED` (`GIT_DIR` без рабочего дерева, а в текущем каталоге нет ни одного файла HEAD: рабочее дерево не проверялось).

Если путь вообще не является репозиторием, сообщается почему, когда причина на диске: переименованный `.git 2`, собственные файлы git только в облаке, каталог git без HEAD, файл `.git`, указывающий на каталог git, которого больше нет, или `core.worktree`, указывающий на папку, которой нет на этой машине (настройка другой машины, принесённая клиентом синхронизации). Если на пути есть `.git`, который git не может использовать, проверка останавливается там (код 2), а не отвечает за внешний репозиторий, как сделал бы сам git.

<a name="install"></a>

## Установка

Требуется git 2.31 или новее. macOS и Linux, amd64 и arm64, без cgo.

```
brew install aliyilmazco/tap/gitbrella
```

```
go install github.com/aliyilmazco/gitbrella/cmd/gitbrella@latest
```

или скачайте архив со страницы releases.

### Проверка релиза

Каждый релиз содержит `checksums.txt` (SHA-256 каждого архива и SBOM), бесключевую подпись cosign `checksums.txt.sigstore.json`, созданную workflow релиза, SPDX SBOM для каждого архива и аттестацию происхождения сборки GitHub (build-provenance attestation). Сначала проверьте подпись, затем архив по подписанному списку (пример — v1.2.3 для Apple silicon). Используйте cosign v3.1.3 или новее (v2.6.5 в линейке v2): старые версии можно обмануть поддельным бандлом (GHSA-fx35-mq7g-6g98).

```sh
cosign verify-blob \
  --certificate-identity 'https://github.com/aliyilmazco/gitbrella/.github/workflows/release.yml@refs/tags/v1.2.3' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  --bundle checksums.txt.sigstore.json checksums.txt
grep ' gitbrella_1.2.3_darwin_arm64.tar.gz$' checksums.txt | shasum -a 256 -c
gh attestation verify gitbrella_1.2.3_darwin_arm64.tar.gz \
  --repo aliyilmazco/gitbrella \
  --signer-workflow aliyilmazco/gitbrella/.github/workflows/release.yml \
  --source-ref refs/tags/v1.2.3 --deny-self-hosted-runners
```

Релиз собирается из отправленного тега workflow `.github/workflows/release.yml` с помощью `.goreleaser.yaml` и остаётся черновиком, пока его не опубликует человек. Бинарники собираются с `-trimpath` и временем коммита, поэтому один и тот же тег и один и тот же релиз Go (workflow берёт последний патч 1.26) дают одинаковые бинарники; архивы и SBOM вокруг них содержат время сборки.

<a name="limits"></a>

## Ограничения

- `fix` исправляет только там, где есть один правильный ответ, а остальное оставляет вам с командой для выполнения; долгосрочное решение — `move-out`, который держит `.git` вне синхронизируемой папки.
- Конфликтные копии, которые сам iCloud создаёт между двумя устройствами, в тестах не воспроизводились; обнаружение протестировано на копиях с тем же именованием.
- Codex не передаёт хукам `workdir` своего инструмента оболочки: команда, которую Codex выполняет в другой папке, проверяется в папке сессии.
- Windows и OneDrive в Windows не тестировались. Для репозиториев reftable выполняются проверки на уровне файлов и проверка неперечисленных таблиц; копии ref там не сравниваются со своими ветками.
- Имена копий с метками, которые имя может содержать намеренно, сопоставляются только там, где имя создаёт сам git, и никогда в рабочем дереве: `index (1)` из Google Drive — для собственных файлов git и в `refs/`; `index-COMPUTER` из OneDrive — для собственных файлов git на верхнем уровне папки OneDrive, с именем устройства, содержащим заглавную букву, не являющимся словом, которым обычно заканчивают имя резервной копии (`index-old`, `config-OLD`, `config-Backup`, `index-BAK` — ваши), и длиной не более 15 символов (более длинное имя Mac будет пропущено); `_conflict-YYYYMMDD-HHMMSS` старого Nextcloud, имена Synology Drive, `.conflicted` pCloud и `.Conflict` Resilio — для собственных файлов git на верхнем уровне (имена старого Nextcloud также в `refs/` и `logs/` рядом с оригиналом в папке Nextcloud). Ветка, на которую указывает какой-либо HEAD (как `ref:` с любыми пробелами или как симлинк), её reflog и каталоги, содержащие её, никогда не откладываются в сторону, как бы они ни назывались. Поэтому `report (1).pdf`, ветка `fix.Conflict`, тег `v1.0.conflicted` или `config-backup` — обычные имена.
- Подмодули проверяются изнутри подмодуля. Из родительского проекта конфликтная копия в `.git/modules/<name>/` обнаруживается, только если рядом лежит оригинал, а подмодуль с именем копии (`lib 2`) сообщается как копия.
- Отсутствующий index связанного рабочего дерева обнаруживается при проверке этого рабочего дерева, а не основного.
- Если `.git` — симлинк на хранилище вне синхронизируемой папки, запускайте git и проверку из связанного рабочего дерева. Из каталога хранилища, где нет ни одного файла, опустевший index выглядит как намеренное «удалить всё» и не блокирует коммит.
- Некоторым намеренным коммитам нужен `--no-verify`: прекращение отслеживания файлов, остающихся на диске, удаление всех файлов там, где нельзя читать объекты, переименование, меняющее только регистр или форму Unicode файла с другой жёсткой ссылкой, а также любой коммит в sparse checkout (в режиме cone или без него), который удаляет или переименовывает отслеживаемый файл либо перемещает его через смену типа (файл, ставший каталогом, каталог, ставший симлинком или подмодулем). Там шаблоны sparse git решают, какие файлы есть на диске, поэтому намеренное удаление нельзя отличить от потерянного index; шаблоны не читаются.
- Если клиент синхронизации вместе с index потерял и сам ref ветки (его loose-файл удалён раньше, чем пришёл новый `packed-refs`), HEAD выглядит как новая ветка, и коммит не блокируется: он начинает новую историю только с подготовленными файлами. Ничего на диске не удаляется, а старая история остаётся в reflog (`git reflog`).
- При разделённом index или там, где нельзя читать объекты (частичный клон с git старше 2.45, альтернативные хранилища только в облаке), index не сравнивается с HEAD пофайлово: обнаруживаются только отсутствующий или пустой index.
- С `core.splitIndex` index, не перечисляющий ни одного файла, не распознаётся (его заголовок учитывает только разделённую часть), поэтому коммит из него не блокируется.
- Хуки: только хуки коммита находятся по процессу git, который их запускает. Другие хуки (`pre-push`, `pre-applypatch`) должны запускать проверку из рабочего дерева, иначе получают отказ (код 2). Там, где процесс git не виден (клиент, который сам запускает хуки, или заблокированный просмотр процессов), проверка использует текущий каталог: тогда, если каталог git не указывает обратно на рабочее дерево (`--separate-git-dir`, `.git.nosync`, `--work-tree`), index без файлов всегда блокирует коммит (для намеренного опустошения используйте `--no-verify`), текущий каталог, не содержащий ни одного файла HEAD, не проверяется как рабочее дерево (`WORKTREE_GUESSED`), а хук, перешедший в другой репозиторий или каталог git, получает отказ (код 2). Хуки приёма (`pre-receive`) не являются поддерживаемым рубежом.
- `move-out`: файл `.git` понимают не все инструменты. Git и инструменты, запускающие git, работают; isomorphic-git (Obsidian Git на мобильных) и инструменты, открывающие `.git` как каталог, — нет.
- `move-out`: переименование или перемещение синхронизируемой папки ломает относительный файл `.git`. Тогда `check` назовёт отсутствующий каталог; верните папку на место или вручную направьте файл `.git` на каталог git.
- `move-out` требует, чтобы синхронизируемая папка находилась в одном и том же месте домашнего каталога на каждом устройстве (у iCloud Drive это всегда так; Dropbox может быть `~/Dropbox` на одном устройстве и `~/Library/CloudStorage/Dropbox` на другом). Если это не так, файл `.git` там указывает в другое место, и `--attach` отказывается (`TARGET_UNEXPECTED`).
- Перенесённый каталог git находится на файловой системе домашнего каталога; опции разместить его в другом месте нет.
- `move-out --prepare` копирует историю устройства на тот момент: переносите вскоре после подготовки, без новых коммитов в промежутке.
- `move-out` и `fix` опробованы в собственной папке iCloud Drive, а не в iCloud-папке приложения (`iCloud~md~obsidian` у Obsidian).
