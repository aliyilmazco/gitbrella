iCloud Drive, Dropbox, OneDrive, Google Drive और Syncthing फ़ाइलों को एक-एक करके सिंक करते हैं। git मानता है कि `.git` डायरेक्टरी एक इकाई के रूप में बदलती है, इसलिए सिंक किए गए फ़ोल्डर में रखी रिपॉज़िटरी में `.git/index 2` और `refs/heads/main 2` जैसी कॉन्फ़्लिक्ट कॉपियाँ, छूटे हुए `index.lock` के पास गायब index, और ऐसे ऑब्जेक्ट जमा हो जाते हैं जो सिर्फ़ क्लाउड में मौजूद हैं। git का अपना FAQ सिंक फ़ोल्डरों में रिपॉज़िटरी रखने से मना करता है, फिर भी डिफ़ॉल्ट सेटिंग्स उन्हें वहीं रखती रहती हैं: macOS पर iCloud डेस्कटॉप और दस्तावेज़, Windows पर OneDrive फ़ोल्डर बैकअप, `Documents/GitHub`।

<p align="center">
  <img src="../../assets/sync-damage.svg" width="820" alt="सिंक क्लाइंट .git को डिवाइसों के बीच फ़ाइल-दर-फ़ाइल कॉपी करता है और index 2 व refs/heads/main 2 जैसी कॉन्फ़्लिक्ट कॉपियाँ, गायब index के पास index.lock, और सिर्फ़ क्लाउड में मौजूद ऑब्जेक्ट छोड़ जाता है">
</p>

`gitbrella check` आम तौर पर एक सेकंड से कम में बता देता है कि रिपॉज़िटरी में यह नुकसान है या नहीं। इसे इस तरह बनाया गया है कि किसी AI एजेंट या git हुक के रिपॉज़िटरी को छूने से पहले चलाया जाए। `gitbrella fix` वह ठीक करता है जिसकी सही मरम्मत का एक ही तरीका है, और `gitbrella move-out` नुकसान को जड़ से खत्म करता है: यह `.git` को सिंक फ़ोल्डर से बाहर ले जाता है और उसकी जगह एक `.git` फ़ाइल छोड़ता है जो वहाँ पॉइंट करती है, ताकि सिंक क्लाइंट आपकी फ़ाइलें ले जाए और git इतिहास अपने पास रखे।

| कमांड | क्या करता है |
| --- | --- |
| `gitbrella check` | नुकसान की रिपोर्ट (सिर्फ़ पढ़ता है) |
| `gitbrella fix` | वह ठीक करता है जिसका एक ही सही उत्तर है |
| `gitbrella move-out` | `.git` को हमेशा के लिए सिंक फ़ोल्डर से बाहर ले जाता है |
| `gitbrella undo` | आख़िरी मरम्मत या स्थानांतरण पलटता है |
| `gitbrella history` | इस डिवाइस पर किए गए बदलावों की सूची |
| `gitbrella prune-backups` | उन बदलावों के पुराने बैकअप हटाता है जिन्हें अब पलटा नहीं जा सकता |
| `gitbrella hook --for claude\|codex` | AI एजेंट के टूल कॉल की सुरक्षा करता है |

## जल्दी शुरू करें

**1. जाँचें।** सिर्फ़ पढ़ना, कोई डाउनलोड नहीं, कोई नेटवर्क नहीं।

```sh
cd ~/Library/Mobile\ Documents/com~apple~CloudDocs/notes
gitbrella check               # exit 0: स्वस्थ, 1: नुकसान, 2: चल नहीं सका
```

**2. ठीक करें।** सिर्फ़ वह जिसका एक ही सही उत्तर है। `--apply` के बिना यह केवल योजना दिखाता है।

```sh
gitbrella fix                 # क्या ठीक करेगा और क्या आप पर छोड़ेगा
gitbrella fix --apply         # ठीक करें; `gitbrella undo --apply` वापस लाता है
```

**3. स्थायी हल।** `.git` को सिंक फ़ोल्डर से बाहर ले जाएँ।

```sh
gitbrella move-out            # क्या होगा और क्या इसे रोकेगा
gitbrella move-out --apply
```

**सुरक्षित रहें।** क्षतिग्रस्त रिपॉज़िटरी में कमिट रोकें:

```sh
printf '#!/bin/sh\nexec gitbrella check\n' > .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit
```

AI एजेंटों के लिए [एजेंटों के लिए](#for-agents) देखें।

## यह क्या वादा करता है

- <img src="../../assets/icons/read-only.svg" width="18" alt=""> **`check` सिर्फ़ पढ़ता है।** यह रिपॉज़िटरी में कभी नहीं लिखता। git केवल पढ़ने वाले कमांड चलाता है, `GIT_OPTIONAL_LOCKS=0` के साथ और ऑटो gc व मेंटेनेंस बंद करके। जोखिम भरे मामलों (index की कॉपी, गायब index, आंशिक क्लोन, स्प्लिट index, स्थानांतरित git डायरेक्टरी) के एंड-टू-एंड टेस्ट जाँच से पहले और बाद में हर फ़ाइल का आकार, mtime और inode दर्ज करते हैं और उनकी तुलना करते हैं।
- <img src="../../assets/icons/no-download.svg" width="18" alt=""> **क्लाउड से कुछ डाउनलोड नहीं करता।** macOS पर यह डिस्क छूने से पहले अपनी प्रोसेस (और जिस git को चलाता है उसके) लिए ऑन-डिमांड डाउनलोड बंद कर देता है; अगर macOS मना कर दे, तो जाँच नहीं चलती (exit 2)। जो फ़ाइल सिर्फ़ iCloud में है, वह रिपोर्ट होती है, लाई नहीं जाती।
- <img src="../../assets/icons/no-network.svg" width="18" alt=""> **नेटवर्क का उपयोग नहीं।** आंशिक क्लोन कभी भी गायब ऑब्जेक्ट नहीं लाता (`GIT_NO_LAZY_FETCH`); 2.45 से पुराने git पर इसके बजाय ऑब्जेक्ट जाँचें छोड़ दी जाती हैं।
- <img src="../../assets/icons/quiet.svg" width="18" alt=""> **स्वस्थ रिपॉज़िटरी पर चुप रहता है।** लॉक को नुकसान तभी माना जाता है जब वह पुराना हो और उस रिपॉज़िटरी (उसके किसी भी वर्कट्री) पर चल रहा कोई भी git उसे न लिख सकता हो: git लॉक लेते समय उसे बनाता है, इसलिए बाद में शुरू हुआ git उसे पकड़े नहीं रख सकता। git की अस्थायी फ़ाइलें और `.git` के अंदर दूसरे टूल्स की फ़ाइलें केवल जानकारी हैं। उपयोग में चल रही 89 स्वस्थ रिपॉज़िटरी पर चलाने से एक भी नुकसान रिपोर्ट नहीं हुआ।

## उपयोग

```
gitbrella check [--json] [--deep] [--provider NAME] [path]
```

Exit कोड: **0** कोई नुकसान नहीं, **1** नुकसान मिला, **2** जाँच नहीं चल सकी। जो कमांड कुछ बदलते हैं (`move-out`, `fix`, `undo`), उनके लिए: **0** योजना बनी, पूरा हुआ या करने को कुछ नहीं (`already`), **1** मना किया (कारणों के साथ), चेतावनियों के साथ पूरा हुआ, या आप पर छोड़ा गया नुकसान बाकी है (`fix` की MANUAL सूची; `check` उसे रिपोर्ट करता रहता है), **2** विफल (रोलबैक या रुका; JSON में जो वापस आया और जर्नल प्रविष्टियाँ रहती हैं) या चल नहीं सका।

`--deep` पूरा `git fsck` भी चलाता है (यह हर ऑब्जेक्ट पढ़ता है, इसलिए अगर ऑब्जेक्ट सिर्फ़ क्लाउड में हैं तो छोड़ दिया जाता है)। `--provider` पाथ से पहचानने के बजाय सिंक क्लाइंट तय कर देता है: `auto` (डिफ़ॉल्ट), `icloud`, `icloud-desktop-documents`, `dropbox`, `onedrive`, `google-drive`, `syncthing`, `nextcloud`, `cloud-storage`, `none`। Syncthing और Nextcloud (या ownCloud) फ़ोल्डर कहीं भी हों, क्लाइंट द्वारा उनके अंदर रखे मार्कर (`.stfolder`, `.sync_*.db`) से पहचाने जाते हैं। `fix` और `move-out` भी वही `--provider` लेते हैं; `check` को दिया गया वही मान दें, क्योंकि कुछ कॉपी नाम सिर्फ़ किसी खास क्लाइंट के लिए गिने जाते हैं। तब JSON में `"providerForced": true` दिखता है।

### git हुक के रूप में

```sh
#!/bin/sh
# .git/hooks/pre-commit
exec gitbrella check
```

<p align="center">
  <img src="../../assets/hook-flow.svg" width="820" alt="git commit pre-commit हुक चलाता है, जो gitbrella check चलाता है: exit 0 पर कमिट आगे बढ़ता है, 1 या 2 पर रुक जाता है">
</p>

क्षतिग्रस्त रिपॉज़िटरी में कमिट रुक जाता है; स्वस्थ रिपॉज़िटरी में सामान्य रूप से होता है। टूल जानता है कि हुक git चला रहा है, इसलिए वह कमिट के अपने लॉक को पुराना लॉक नहीं समझता।

**कौन-सी रिपॉज़िटरी जाँची जाती है।** कमिट हुक में (git इन्हें `GIT_INDEX_FILE` या एब्सोल्यूट `GIT_DIR` देता है) रिपॉज़िटरी उस git प्रोसेस से ढूँढी जाती है जिसने हुक चलाया, इसलिए हुक पहले डायरेक्टरी बदल सकता है: git डायरेक्टरी में, उसकी hooks डायरेक्टरी में, या किसी भी रिपॉज़िटरी से बाहर की डायरेक्टरी में। जब git एब्सोल्यूट `GIT_DIR` से रिपॉज़िटरी बताता है (लिंक्ड वर्कट्री, सबमॉड्यूल, अलग git डायरेक्टरी), तो हुक कहीं भी जाए, उसके अंदर का हर git कमांड उसी पर काम करता है, और जाँच भी। अन्यथा यह देखता है कि मौजूदा डायरेक्टरी git के लिए खुद कहाँ ले जाती है (वहाँ रिलेटिव `GIT_DIR` जिस git डायरेक्टरी को दिखाता है, या वहाँ से मिली रिपॉज़िटरी); अगर वह कोई दूसरी रिपॉज़िटरी या उसी रिपॉज़िटरी का दूसरा वर्कट्री है (वहाँ जाने वाला हुक, या कमिट मैसेज एडिटर), तो गलत रिपॉज़िटरी के बारे में जवाब देने के बजाय मना कर देता है (exit 2)।

पाथ के बिना यह वह रिपॉज़िटरी जाँचता है जो git ने हुक को एक्सपोर्ट की (`GIT_DIR`), इसलिए `--git-dir` वाले dotfiles सेटअप और अपने ही वर्कट्री के अंदर रखी git डायरेक्टरी भी काम करती हैं। पाथ के बिना यह शेल में सेट `GIT_DIR` का भी पालन करता है; git के विपरीत, यह मौजूद न होने वाले `GIT_DIR` को अनदेखा करता है और ऐसे लिंक्ड वर्कट्री को, जिसका पीछा नहीं किया जा सकता, मौजूदा डायरेक्टरी को वर्कट्री मानने के बजाय अस्वीकार करता है।

**वह index जिसे कमिट दर्ज करता है।** जब `GIT_INDEX_FILE` git डायरेक्टरी के अंदर किसी फ़ाइल की ओर इशारा करता है (कमिट हुक के लिए git ऐसा ही सेट करता है), तो वही पढ़ा जाता है। अगर कमिट जो index दर्ज करेगा वह गायब या खाली है, या अब वर्कट्री में मौजूद HEAD फ़ाइलों को सूचीबद्ध नहीं करता, तो कमिट उन फ़ाइलों को हटाया हुआ दर्ज करने से पहले रोक दिया जाता है। आपके द्वारा `GIT_INDEX_FILE` से बताई गई किसी दूसरी जगह की index फ़ाइल नहीं पढ़ी जाती: हुक के अंदर उसकी जगह रिपॉज़िटरी का अपना index जाँचा जाता है, और यह वेरिएबल सेट रखकर हाथ से चलाई गई जाँच अस्वीकार की जाती है (exit 2)।

**जान-बूझकर हटाना।** डिस्क पर रहने वाली फ़ाइलों को ट्रैक करना बंद करने के लिए (`git rm --cached`, किसी ऐसी डायरेक्टरी को अनट्रैक करना जो अब ignore है), या फ़ाइलें डिस्क पर रहते हुए जान-बूझकर "सब हटाओ" कमिट करने के लिए (`git rm -r --cached .`), `git commit --no-verify` से हुक छोड़ दें।

### हुक मैनेजर के साथ

- **pre-commit** (pre-commit.com): इस रिपॉज़िटरी को हुक id `gitbrella` (pre-commit इसे Go से बनाता है) या `gitbrella-system` (PATH पर मौजूद बाइनरी) के साथ जोड़ें; `.pre-commit-hooks.yaml` देखें।
- **lefthook**: `remotes` के ज़रिए `hooks/lefthook.yml` इम्पोर्ट करें।
- **husky**: `.husky/pre-commit` जिसमें `gitbrella check` हो।
- **Overcommit**: `PreCommit: { Gitbrella: { enabled: true, required_executable: gitbrella, command: [gitbrella, check] } }`, फिर `overcommit --sign`।

इन सभी में कोई भी गैर-शून्य exit कमिट रोक देता है, इसलिए जो जाँच नहीं चल सकी (exit 2) वह भी उसे रोकती है। Aider `--no-verify` के साथ कमिट करता है जब तक `git-commit-verify: true` सेट न हो, और तब कोई कमिट हुक बिल्कुल नहीं चलता। Obsidian Git (डेस्कटॉप) आपके सिस्टम के git से कमिट करता है और हुक चलाता है; `gitbrella` वाले फ़ोल्डर को उसकी "Additional PATH" सेटिंग में डालें, क्योंकि Dock से खोले गए ऐप्स को शेल का PATH नहीं मिलता। मोबाइल पर Obsidian Git (isomorphic-git) कोई हुक नहीं चलाता।

<a name="for-agents"></a>

### एजेंटों के लिए

`--json` वही रिपोर्ट एक स्थिर, संस्करण वाले दस्तावेज़ के रूप में प्रिंट करता है (`schemaVersion: 1`, `findings` हमेशा एक सूची)। फ़ैसला exit स्टेटस पर करें, और निष्कर्ष उपयोगकर्ता को दिखाएँ।

एजेंटों के अपने हुक टूल कॉल को सिर्फ़ exit 2 पर रोकते हैं: exit 1 ("नुकसान मिला") कॉल को आगे जाने देता है। `gitbrella hook --for claude|codex` उनके हुक की भाषा बोलता है। यह वह इवेंट पढ़ता है जो एजेंट stdin पर देता है:

<p align="center">
  <img src="../../assets/agent-hook.svg" width="820" alt="एजेंट का टूल कॉल gitbrella hook से होकर जाता है: पढ़ना और संपादन आगे बढ़ते हैं; क्षतिग्रस्त रिपॉज़िटरी में git लेखन और .git में लेखन exit 2 से रुकते हैं">
</p>

- **टूल कॉल से पहले** (`PreToolUse`): क्षतिग्रस्त रिपॉज़िटरी में, लिखने वाला git कमांड (commit, add, reset, rebase, push, और कोई भी चीज़ जिसके बारे में ज्ञात न हो कि वह सिर्फ़ पढ़ती है) और `.git` में लेखन कॉल को रोकते हैं (exit 2, कारण एजेंट के लिए stderr पर)। पढ़ना, आपकी फ़ाइलों का संपादन, `git restore` और खुद `gitbrella` आगे बढ़ते हैं, ताकि नुकसान देखा और ठीक किया जा सके।
  - *अनुपयोगी रिपॉज़िटरी।* जहाँ git की फ़ाइलें सिर्फ़ क्लाउड में हैं, या git रिपॉज़िटरी का बिल्कुल उपयोग नहीं कर सकता (नाम बदला हुआ `HEAD`, कहीं न पॉइंट करने वाली `.git` फ़ाइल), वहाँ हर git कमांड रुकता है: वह या तो अटक जाएगा या किसी बाहरी रिपॉज़िटरी पर काम करेगा। वहाँ `.git` में लेखन आगे बढ़ता है: वह मरम्मत `.git` के अंदर हाथ से की जाती है, जैसा कारण में बताया गया है (`mv '.git/HEAD 2' .git/HEAD`)। `core.worktree` संकेत में बताया गया उपाय (`git config --file … --unset core.worktree`) भी आगे बढ़ता है।
  - *कौन-सी रिपॉज़िटरी।* वह जिसमें वे फ़ाइलें हैं जिन पर कॉल काम करता है (Codex पैच अपनी फ़ाइलें बताता है; `.git` के अंदर का पाथ उसके ऊपर के वर्कट्री में गिना जाता है)। शेल कमांड के लिए, सेशन का फ़ोल्डर और हर वह फ़ोल्डर जिसमें उसके git कमांड चलते हैं (`cd DIR`, `pushd`, `git -C DIR`, `--git-dir`, `--work-tree`, `GIT_DIR`, `env -C`, `bash -c '…'`), लिखने वाले पहले, ज़्यादा से ज़्यादा पाँच; जब कोई लिखने वाला समा नहीं पाता, तो कॉल एक सूचना के साथ गुज़र जाता है। हर फ़ोल्डर को इस पर परखा जाता है कि कॉल वहाँ क्या करता है: क्षतिग्रस्त सेशन फ़ोल्डर से `git -C ../sound commit` आगे बढ़ता है। जो फ़ोल्डर रिपॉज़िटरी नहीं है और bare रिपॉज़िटरी चुपचाप गुज़र जाते हैं।
  - *जब जाँच नहीं चल पाती।* जो भी चीज़ जाँच को चलने से रोके (20 सेकंड का `--timeout` भी, जो पूरे कॉल के लिए एक ही समय-सीमा है), वह कॉल को एक सूचना के साथ जाने देती है; `--fail-open` वहाँ भी यही करता है जहाँ git रिपॉज़िटरी का उपयोग नहीं कर सकता।
  - *कमांड कैसे पढ़ा जाता है।* उसे पढ़ा जाता है, कभी चलाया नहीं जाता: कोट्स, टिप्पणियाँ, सबशेल, सब्स्टिट्यूशन (बिना कोट वाले heredoc के अंदर भी), heredoc, उसके सेट किए वेरिएबल, `&&`, `||`, `if`, `case` और लूप (`cd a || cd b` के बाद या मौजूद न होने वाले फ़ोल्डर में `cd` के बाद, हर वह फ़ोल्डर गिना जाता है जहाँ शेल हो सकता है; `for` लूप हर मान के लिए एक बार पढ़ा जाता है), रैपर (`timeout`, `sudo`, `nice`, `xargs`, `env`), और शेल को दी गई स्क्रिप्ट (`-c`, `eval`, `watch`, `source`, कोई फ़ाइल, कोई heredoc, `bash < f`, `sh` में पाइप)। कमांड द्वारा परिभाषित फ़ंक्शन और alias वहीं पढ़े जाते हैं जहाँ उन्हें बुलाया जाता है। पाथ से चलाई गई या शेल को दी गई शेल स्क्रिप्ट (`./deploy.sh`, `bash deploy.sh`) पढ़ी जाती है अगर वह इस मशीन पर एक छोटी फ़ाइल है (symlink के ज़रिए भी; एक बार, भले वह खुद को चलाए); `make`, `npm run` और इसी तरह की चीज़ें नहीं पढ़ी जातीं।
  - *क्या लेखन गिना जाता है।* किसी दूसरे प्रोग्राम का `.git` में लिखना (`rm .git/index.lock`, `> .git/HEAD`, `cd .git && rm index.lock`, `.git/config` पर `sed -i`, `.git` वाले फ़ोल्डर पर `rm -rf` या `find -delete`, शेल के ज़रिए Codex पैच) `.git` में लेखन माना जाता है; `.git` को कहीं और कॉपी करना, `tar` करना या पढ़ना नहीं। `gh pr checkout` और `git-lfs` लिखने वाले git कमांड माने जाते हैं।
  - *संदेह होने पर।* इनमें से हर एक लिखने वाला git कमांड माना जाता है: 5000 कदम या `--timeout` के आधे से लंबा पढ़ना (उस फ़ोल्डर में जिसे यह तय नहीं कर सका); ऐसी जगह शब्द `git` जिसका पढ़ना अनुसरण नहीं करता; ऐसे प्रोग्राम से शेल में पाइप की गई स्क्रिप्ट जिसका पढ़ना अनुसरण नहीं करता (`curl … | sh`), जहाँ वह चलती है; शेल को दी गई ऐसी स्क्रिप्ट जो मौजूद है पर पढ़ी नहीं जा सकती (बहुत बड़ी, सिर्फ़ क्लाउड में), जहाँ वह चलती है। जब यह तय नहीं हो पाता कि कोई git कमांड किस फ़ोल्डर में लिखता है (`cd "$(…)"`, `for d in */`), तो वह कमांड हर जाँचे गए फ़ोल्डर में गिना जाता है और कॉल को सूचना मिलती है।
- **सेशन शुरू होने पर** (`SessionStart`): stdout पर एक पंक्ति, जिसे एजेंट संदर्भ के रूप में पढ़ता है; यह बताती है कि रिपॉज़िटरी सिंक फ़ोल्डर में है (जब तक उसकी git डायरेक्टरी पहले से बाहर न हो) और क्या क्षतिग्रस्त है। यह कभी नहीं रोकती।

हुक कुछ नहीं बदलता। Claude Code के लिए, `.claude/settings.json` में:

```json
{
  "hooks": {
    "SessionStart": [{"hooks": [{"type": "command", "command": "gitbrella hook --for claude"}]}],
    "PreToolUse": [{"matcher": "Edit|Write|MultiEdit|NotebookEdit|Bash",
                    "hooks": [{"type": "command", "command": "gitbrella hook --for claude"}]}]
  }
}
```

Codex के लिए, `.codex/hooks.json` में (Codex किसी हुक को तभी चलाता है जब आप `/hooks` में उस पर भरोसा कर लें):

```json
{
  "hooks": {
    "SessionStart": [{"hooks": [{"type": "command", "command": "gitbrella hook --for codex"}]}],
    "PreToolUse": [{"matcher": "Bash|apply_patch",
                    "hooks": [{"type": "command", "command": "gitbrella hook --for codex"}]}]
  }
}
```

जाँच इन फ़ोल्डरों में से हर एक के लिए एक बार चलती है, आम तौर पर हर बार 0.1 से 0.4 सेकंड, इसलिए किसी रिपॉज़िटरी के कई फ़ोल्डरों में फैला पैच उस रिपॉज़िटरी को कई बार जाँचता है; `--timeout` पूरे कॉल को सीमित करता है।

<a name="repairing"></a>

## मरम्मत

```sh
gitbrella fix                 # क्या ठीक करेगा और क्या आप पर छोड़ेगा
gitbrella fix --apply         # ठीक करें
gitbrella undo --apply        # सब वापस करें
gitbrella history             # यहाँ किए गए बदलाव, उनके बैकअप और आकार
gitbrella prune-backups       # वे बैकअप जिनकी किसी undo को अब ज़रूरत नहीं
```

<p align="center">
  <img src="../../assets/fix-flow.svg" width="820" alt="fix योजना दिखाता है; fix --apply हर कदम दर्ज करता है, फिर जाँच दोबारा चलती है: पूरा हुआ या रोलबैक; undo --apply आख़िरी बदलाव पलटता है">
</p>

`check` हर नुकसान के नीचे बताता है कि `fix` उसे ठीक करता है या नहीं (`repair:`, और JSON में `"repair": "fix"` या `"manual"`), और अगर जाँच को provider दिया गया था तो `fix --provider NAME` बताता है। कमिट हुक के अंदर यह कुछ नहीं पूछता।

`fix` सिर्फ़ वहीं ठीक करता है जहाँ एक ही सही उत्तर हो और ऐसी किसी चीज़ पर ओवरराइट न हो जो आपने शायद चाही हो:

| नुकसान | मरम्मत |
| --- | --- |
| `.git` में अपने मूल के पास रखी कॉन्फ़्लिक्ट कॉपियाँ (`HEAD 2`, `refs/heads/main 2`, `refs 2`, `packed-refs 2`, Dropbox और Syncthing की कॉपियाँ, और ref लॉक की कॉपी जैसे `refs/heads/main 2.lock`); index की कॉपी सिर्फ़ तब जब वह index जैसी ही हो या HEAD के बराबर वैध index हो | बैकअप में ले जाई जाती हैं; जिस ऑब्जेक्ट (कमिट, टैग, ट्री या फ़ाइल) को सिर्फ़ कॉपी दिखाती है, वह पहले `refs/gcd-rescue/<name>` के रूप में सुरक्षित किया जाता है |
| छूटी हुई rebase डायरेक्टरी, `desktop.ini`, `Icon` और git द्वारा न बनाई गई ऐसी ही फ़ाइलें (जब तक git किसी को ब्रांच के रूप में न पढ़े या उसका नाम किसी ऑब्जेक्ट का नाम न हो), वर्कट्री में `.git` की ऐसी कॉपी जिसके कमिट रिपॉज़िटरी में हैं | बैकअप में ले जाई जाती हैं |
| गायब index जिसकी कहीं कोई कॉपी या लॉक नहीं | HEAD से बनाया जाता है (`git read-tree HEAD`: फ़ाइलें नहीं छुई जातीं), सिर्फ़ तब जब बनाने के लिए कोई कमिट हो (अगर HEAD का कमिट भी गायब है, तो पहले नीचे बताए तरीके से लाया जाता है) और sparse checkout के बाहर |
| ऐसा index जो कोई फ़ाइल सूचीबद्ध नहीं करता (sparse checkout के बाहर वैध, बिना स्प्लिट वाला index) | बैकअप में ले जाया जाता है और HEAD से बनाया जाता है: उसमें कुछ भी स्टेज नहीं था |
| अनाथ `index.lock` जो HEAD के बराबर वैध index है | वही index बन जाता है |
| खाली ब्रांच फ़ाइल | वह कमिट जो उसके reflog ने आख़िर में दर्ज किया |
| `.git.nosync` जिसे git किसी कमिट में जोड़ देता | `.git/info/exclude` में `/.git.nosync/` पंक्ति |
| HEAD का गायब कमिट, या खाली loose ऑब्जेक्ट फ़ाइल (बगल में कोई कॉपी नहीं) | खाली फ़ाइल बैकअप में जाती है और ऑब्जेक्ट दोबारा लाए जाते हैं (`git fetch --refetch`, git 2.36 या नया) `--remote` से, नहीं तो ब्रांच के remote से, नहीं तो `origin` से, नहीं तो इकलौते remote से; remote की ब्रांचें और टैग एक अस्थायी `refs/gcd-fetch/` नेमस्पेस में लाए जाते हैं जो बाद में हटा दिया जाता है, इसलिए कोई ref नहीं बदलता। अगर remote ऑब्जेक्ट वापस नहीं लाता, तो मरम्मत रोलबैक होती है |
| `fix --deep` के साथ: वे ऑब्जेक्ट जिन्हें `git fsck` ने क्षतिग्रस्त बताया | remote की ब्रांचों और टैग का हर ऑब्जेक्ट इसी तरह दोबारा लाया जाता है; फिर `git fsck` दोबारा चलता है और अगर वह अब भी त्रुटियाँ बताता है (ऐसा ऑब्जेक्ट जो किसी remote पर नहीं, बची हुई खराब फ़ाइल), तो मरम्मत रोलबैक होती है |
| आपकी अपनी फ़ाइलों की कॉन्फ़्लिक्ट कॉपियाँ (`notes 2.md`) जिन्हें git ट्रैक नहीं करता और जिनमें मूल फ़ाइल जैसे ही बाइट्स हैं | बैकअप में ले जाई जाती हैं (`git add -A` उन्हें कमिट कर देता); जो कॉपी अलग है, ट्रैक की जाती है, लिंक है, सिर्फ़ क्लाउड में है या सबमॉड्यूल में है, वह रहती है |
| किसी दूसरी मशीन का एक घंटे से पुराना `gc.pid`; `gc.log` | बैकअप में ले जाए जाते हैं, ताकि git का ऑटो gc यहाँ फिर से चले |
| `.git` या वैकल्पिक ऑब्जेक्ट स्टोर की सिर्फ़ क्लाउड वाली फ़ाइलें | डाउनलोड की जाती हैं, और कुछ नहीं: तब तक जाँच ऑब्जेक्ट नहीं पढ़ सकती, इसलिए बाकी नुकसान अगले `fix` रन के लिए MANUAL के रूप में सूचीबद्ध होता है |

बाकी सब कुछ MANUAL के रूप में सूचीबद्ध होता है, साथ में चलाने के लिए कमांड। इसमें वह हर चीज़ शामिल है जिसमें ऐसा काम हो सकता है जो कहीं और नहीं है:
- क्षतिग्रस्त index (git शायद अब भी उसे स्टेज किए गए काम के साथ पढ़ सके);
- HEAD से अलग index की कॉपी या `index.lock`, और `index.lock` की कॉपी;
- ऐसी कॉपी जिसका मूल गायब है (वही इकलौती हो सकती है: उसे वापस रखें; अगर वह लॉक की कॉपी है, तो उसे सुरक्षित करके एक तरफ़ रखा जाता है);
- ऐसा लॉक जिसे इस मशीन का कोई git नहीं पकड़े है (किसी दूसरे डिवाइस या कंटेनर का git पकड़े हो सकता है; सलाह में उसके अंदर का कमिट बताया जाता है);
- 100 से ज़्यादा ऑब्जेक्ट बताने वाली कॉपी (लंबा reflog);
- किसी HEAD द्वारा बताई गई ब्रांच, उसके reflog, या उसे रखने वाली डायरेक्टरी की कॉपी (git उसे पढ़ता है, नाम चाहे जैसा दिखे)।

और वह सब कुछ जहाँ fix को दो संस्करणों में से चुनना पड़ता या जहाँ वह कॉपी के कमिट ज़िंदा नहीं रख सकता:
- ऑब्जेक्ट स्टोर की हर चीज़: कॉपियाँ, किसी ऑब्जेक्ट के नाम वाली फ़ाइलें (देखें कि कौन-सी अपने हैश से मेल खाती है), खाली ऑब्जेक्ट फ़ाइलें जिनके लिए लाने को कोई remote नहीं;
- सबमॉड्यूल की git डायरेक्टरी की हर चीज़ (सबमॉड्यूल में `fix` चलाएँ);
- ब्रांच की ऐसी कॉपी जो ऐसे कमिट को बताती है जो अभी यहाँ नहीं पहुँचा (वह अब भी आ सकता है);
- वर्कट्री में `.git` की कॉपी जिसमें ऐसे कमिट हैं जो रिपॉज़िटरी में नहीं (कौन-सा मौजूदा है, यह आप तय करते हैं);
- खाली फ़ाइल जिसके बगल में उसकी या उसकी डायरेक्टरी की कॉपी है;
- टूटी हुई लिंक्ड-वर्कट्री एडमिन डायरेक्टरी (`git worktree repair`);
- ऐसा index जिसने डिस्क पर अब भी मौजूद फ़ाइलें खो दी हैं (जान-बूझकर अनट्रैक करना भी ऐसा ही दिखता है; जब और कुछ स्टेज न हो, तो सलाह बताती है कि `git read-tree HEAD` उन्हें बिना कुछ खोए वापस लाता है);
- `--deep` के बिना या बिना remote के, वे ऑब्जेक्ट जिन्हें `git fsck` ने क्षतिग्रस्त बताया।

`fix` reftable रिपॉज़िटरी को बिल्कुल नहीं छूता; वहाँ `check` का `REFTABLE_TABLE_UNLISTED` निष्कर्ष बताता है कि दूसरे डिवाइस के refs कैसे सुरक्षित रखें। बैकअप रिपॉज़िटरी की डिस्क पर होना चाहिए, ताकि fix जो एक तरफ़ रखता है वह एक कदम में हिल सके; नहीं तो `fix` मना करता है (सिर्फ़ डाउनलोड वाली मरम्मत कुछ नहीं हिलाती और उसे इसकी ज़रूरत नहीं)।

हर कदम होने से पहले दर्ज किया जाता है, और अंत में जाँच दोबारा चलती है: अगर जो ठीक किया वह अब भी रिपोर्ट होता है या नया नुकसान दिखता है, तो कदम पलट दिए जाते हैं। बीच में रोका गया fix उस रिपॉज़िटरी में `--apply` के साथ चलाए गए अगले बदलाव वाले कमांड द्वारा रोलबैक होता है, जो उसके बाद रुक जाता है; उसे फिर से चलाएँ। 30 सेकंड बाद (`--watch`) `fix` एक बार और जाँचता है: लौटा हुआ नुकसान सिंक क्लाइंट वापस लाया है, और स्थायी इलाज `move-out` है।

`undo` सबसे पहले सबसे नया बदलाव पलटता है, चाहे मरम्मत हो या स्थानांतरण। जिस कदम का परिणाम मरम्मत के बाद बदल गया है, उसे जैसा है वैसा छोड़कर सूचीबद्ध किया जाता है, कभी ओवरराइट नहीं: git ने दोबारा बनाए index को फिर से लिखा, सिंक क्लाइंट कॉपी वापस लाया, rescue ref खिसका, बैकअप हटाया गया, या `.git` हिलाया गया। rescue ref तब तक रहता है जब तक वह जिस कॉपी को ज़िंदा रखता है वह बैकअप में है। डाउनलोड की गई फ़ाइलें डिस्क पर रहती हैं और दोबारा लाए गए ऑब्जेक्ट ऑब्जेक्ट स्टोर में: दोनों में से कोई किसी चीज़ की जगह नहीं लेता। बाकी पलट दिया जाता है और undo पूरा होता है, ताकि उससे पहले का बदलाव आगे पलटा जा सके।

`history` इस डिवाइस द्वारा रिपॉज़िटरी में किए गए बदलाव (मरम्मत, स्थानांतरण, undo), हर एक का बैकअप उसके आकार के साथ, और यह कि `undo` अगला कौन-सा पलटेगा, सूचीबद्ध करता है। `prune-backups`, सिर्फ़ `--apply` के साथ, उन बदलावों के बैकअप हटाता है जो पलटे जा चुके हैं, रोलबैक हो चुके हैं या कभी पलटे नहीं जा सकते थे (undo, prepare, attach) और जिनका आख़िरी कदम `--older-than` (डिफ़ॉल्ट `720h`) से पुराना है। जो मरम्मत या स्थानांतरण अब भी पलटा जा सकता है, वह अपना बैकअप रखता है, भले उसके ऊपर नए बदलाव हों।

<a name="moving-git-out-of-the-synced-folder"></a>

## .git को सिंक फ़ोल्डर से बाहर ले जाना

```sh
gitbrella move-out            # क्या होगा और क्या इसे रोकेगा
gitbrella move-out --apply    # करें
gitbrella undo --apply        # वापस ले आएँ
```

<p align="center">
  <img src="../../assets/move-out.svg" width="860" alt="पहले: .git सिंक फ़ोल्डर के अंदर। move-out के बाद: सिंक फ़ोल्डर में एक .git फ़ाइल बाहर ~/.local/share/gitbrella/gitdirs/notes-1a2b3c4d की ओर इशारा करती है">
</p>

`move-out` `.git` को `~/.local/share/gitbrella/gitdirs/<name>` में कॉपी करता है (macOS पर एक APFS क्लोन: कोई जगह नहीं लेता), फ़ाइल-दर-फ़ाइल साबित करता है कि कॉपी एक जैसी है, मूल को `~/Library/Application Support/gitbrella` (Linux: `$XDG_STATE_HOME/gitbrella`) के अंदर बैकअप में ले जाता है, और `gitdir: ../../../../.local/share/gitbrella/gitdirs/notes-1a2b3c4d` जैसी `.git` फ़ाइल लिखता है। पाथ रिलेटिव है, इसलिए हर वह डिवाइस जो फ़ोल्डर को होम के नीचे उसी जगह रखता है, वही `.git` फ़ाइल लिखता है। फिर यह जाँचता है कि git वही HEAD, स्टेटस, कॉन्फ़िग और hooks डायरेक्टरी पाता है, और 30 सेकंड तक (`--watch`) देखता है कि सिंक क्लाइंट `.git` को नहीं छूता, और iCloud में नई फ़ाइल अपलोड करता है। अंतिम तुलना से पहले मूल को एक तरफ़ रखा जाता है, इसलिए कॉपी के दौरान घुसा कोई भी लेखन पकड़ा जाता है और स्थानांतरण पलट दिया जाता है। iCloud में, जब तक iCloud रिपॉज़िटरी अपलोड कर रहा है, `move-out` मना करता है; `--wait-upload 10m` इसके बजाय उतनी देर तक इंतज़ार करता है।

हर बदलाव होने से पहले एक जर्नल में दर्ज होता है, उसके द्वारा बनाई गई हर चीज़ के डिवाइस और inode (और `.git` फ़ाइल के बाइट्स) के साथ; रोलबैक और कुछ नहीं छूता। अगर प्रोसेस बीच में बंद हो जाए, तो अगला `move-out --apply` (या `undo --apply`) उसे पूरा या रोलबैक करके वहीं रुक जाता है (आगे बढ़ने के लिए कमांड फिर चलाएँ); अधूरा बदलाव फ़ोल्डर के inode से मिलता है, भले पाथ अलग तरह से लिखा हो, नाम बदलने के बाद हो, या किसी दूसरी रिपॉज़िटरी के अंदर हो। इस बीच `check` अधूरे बदलाव को नुकसान के रूप में रिपोर्ट करता है। git के स्थानांतरित डायरेक्टरी का उपयोग शुरू करने के बाद उसके ऊपर कुछ भी रोलबैक नहीं होता: अगर उसमें कुछ ऐसा है जो मूल में नहीं है, तो कमांड रुककर दोनों का नाम बताता है। कुछ भी हटाया नहीं जाता: मूल बैकअप में तब तक रहता है जब तक आप उसे न हटाएँ। `undo` अभी उपयोग में चल रही git डायरेक्टरी को, स्थानांतरण के बाद किए गए कमिट के साथ, वापस लाता है; स्थानांतरण से पहले का बैकअप जैसा है वैसा रहता है। अगर सिंक क्लाइंट ने `.git` फ़ाइल को evict कर दिया है (इस Mac पर सिर्फ़ उसका नाम बचा है), तो `undo` और रिकवरी पहले उसे डाउनलोड करने को कहते हैं: उसे पढ़ने से डाउनलोड होगा, और यह टूल ऐसा कभी नहीं करता।

अगर रोलबैक को मूल (बैकअप में) और एक नया `.git` (स्थानांतरण रुकने के बाद आपके या सिंक क्लाइंट द्वारा बनाया गया) दोनों मिलते हैं, तो यह किसी पर ओवरराइट नहीं करता और यह बताता है: दोनों की तुलना करें, जो `.git` नहीं चाहिए उसे फ़ोल्डर से बाहर ले जाएँ, और कमांड फिर चलाएँ।

यह मना करता है (exit 1, कारणों के साथ) जब git या git लॉक पकड़े कोई चीज़ रिपॉज़िटरी पर चल रही हो, merge या rebase के दौरान, जब `.git` की फ़ाइलें सिर्फ़ क्लाउड में हों, जब iCloud अब भी फ़ोल्डर अपलोड कर रहा हो, जब `.git` में कोई सॉकेट हो (चलता हुआ `git fsmonitor--daemon`), जब स्थानांतरण के बाद दो git डायरेक्टरी मौजूद हों, और ऐसे लेआउट के लिए जिनके लिंक टूट जाएँगे: लिंक्ड वर्कट्री, सबमॉड्यूल, उधार लिए गए ऑब्जेक्ट (`alternates`), ऐसा `.git` जो symlink है या खुद git डायरेक्टरी नहीं है। `check` द्वारा मिला दूसरा नुकसान जैसा है वैसा ले जाया जाता है और आगे ले जाया गया के रूप में सूचीबद्ध होता है: बाद में `check` फिर चलाएँ।

### दूसरे डिवाइस

सिंक क्लाइंट फ़ोल्डर सिंक करने वाले हर दूसरे डिवाइस पर `.git` हटा देता है और वहाँ `.git` फ़ाइल पहुँचा देता है। उनका इतिहास सुरक्षित रखने के लिए:

<p align="center">
  <img src="../../assets/other-devices.svg" width="820" alt="1: हर दूसरे डिवाइस पर move-out --prepare --apply। 2: एक डिवाइस पर move-out --apply। 3: हर दूसरे डिवाइस पर move-out --attach --apply">
</p>

1. हर दूसरे डिवाइस पर, स्थानांतरण से पहले: `gitbrella move-out --prepare --apply` उस डिवाइस के `.git` को वहाँ कॉपी करता है जहाँ `.git` फ़ाइल इशारा करेगी।
2. एक डिवाइस पर: `gitbrella move-out --apply`।
3. हर दूसरे डिवाइस पर, `.git` फ़ाइल पहुँचने के बाद: `gitbrella move-out --attach --apply`। जो डिवाइस तैयार नहीं किया गया, वह इसके बजाय इतिहास क्लोन करता है: `--attach --from <remote URL> --apply`। किसी भी तरह से वर्कट्री नहीं छुई जाती।

`.git` फ़ाइल सिंक क्लाइंट के ज़रिए आती है, इसलिए attach उस पर सिर्फ़ उतना भरोसा करता है जितना इस डिवाइस के रिकॉर्ड अनुमति दें: उसे इस डिवाइस के `~/.local/share/gitbrella/gitdirs` के अंदर इशारा करना चाहिए, और वहाँ पहले से मौजूद डायरेक्टरी का उपयोग तभी होता है जब `--prepare` ने उसे इसी रिपॉज़िटरी के लिए बनाया हो।

इसके बाद से सिंक क्लाइंट फ़ाइलें ले जाता है, इतिहास नहीं। कमिट किसी remote के ज़रिए साझा करें। जिस डिवाइस की फ़ाइलें सिंक क्लाइंट पहले ही अपडेट कर चुका है, वहाँ `git pull` मना करता है ("would be overwritten"): `git fetch` और `git reset --mixed @{u}` का उपयोग करें, जो ब्रांच और index को आगे बढ़ाता है और सिंक की गई फ़ाइलों को जैसा है वैसा छोड़ता है।

| `INDEX_COPY` | index की कॉन्फ़्लिक्ट कॉपी (`index 2`; Dropbox, Syncthing, Nextcloud/ownCloud, Proton Drive और Seafile के नाम; Google Drive का `index (1)`, OneDrive फ़ोल्डर में OneDrive का `index-COMPUTER`, और पुराने Nextcloud, Synology Drive, pCloud व Resilio के नाम सिर्फ़ git की अपनी फ़ाइलों के नामों से मिलाए जाते हैं); बताता है कि यह वैध index है या नहीं और HEAD से मेल खाता है या नहीं |
| `REF_COPY` | ब्रांच या टैग ref की कॉन्फ़्लिक्ट कॉपी; बताता है कि कॉपी पुरानी, नई, अलग राह पर है या गायब कमिट बताती है |
| `COPY_IN_GITDIR` | `.git` में कोई भी दूसरी कॉन्फ़्लिक्ट कॉपी |
| `INDEX_MISSING` | index गायब है; git हर फ़ाइल को हटाई हुई दिखाता है (कमिट हुक में: कमिट हर फ़ाइल हटा देगा) |
| `INDEX_EMPTY` | HEAD की फ़ाइलें अब भी वर्कट्री में होने के बावजूद index कोई फ़ाइल सूचीबद्ध नहीं करता, जैसा तब होता है जब सिंक क्लाइंट द्वारा index हटाने के बाद git उसे दोबारा बनाता है; कमिट हर फ़ाइल हटा देगा |
| `INDEX_SHRUNK` | index अब वर्कट्री में मौजूद HEAD फ़ाइलें सूचीबद्ध नहीं करता (sparse checkout में: कोई भी HEAD फ़ाइल), जैसा तब होता है जब सिंक क्लाइंट द्वारा index हटाने के बाद git उसे स्टेज की गई फ़ाइलों से दोबारा बनाता है; कमिट उन्हें हटा देगा। नाम बदलना, symlink या `.gitmodules` में घोषित सबमॉड्यूल बन चुकी डायरेक्टरी, और डिस्क से भी हटाई गई फ़ाइलें नहीं गिनी जातीं; जब HEAD की फ़ाइलें सूचीबद्ध नहीं हो पातीं, तो असत्यापित के रूप में रिपोर्ट होता है |
| `HEAD_COMMIT_MISSING` | HEAD ऐसा कमिट बताता है जो रिपॉज़िटरी में नहीं है (ref अपने ऑब्जेक्ट से पहले पहुँच गया) |
| `ORPHAN_INDEX_LOCK` | index गायब है और एक पुराना `index.lock` बचा है (अक्सर पूरा index) |
| `INDEX_INVALID` | index अपना चेकसम पास नहीं करता |
| `STALE_LOCK` | ऐसा git लॉक जिसे कोई चलता हुआ git नहीं पकड़ सकता: रिपॉज़िटरी पर कोई नहीं चल रहा, या सभी लॉक लिखे जाने के बाद शुरू हुए। सिर्फ़ इस मशीन की git प्रोसेस दिखती हैं: लॉक हटाने से पहले पक्का करें कि कोई git रिपॉज़िटरी का उपयोग किसी कंटेनर में, फ़ोल्डर साझा करने वाली दूसरी मशीन पर, या git एम्बेड करने वाले किसी ऐप में नहीं कर रहा |
| `DATALESS_IN_GITDIR` | `.git` की फ़ाइलें सिर्फ़ क्लाउड में हैं; ऑब्जेक्ट जाँचें छोड़ी गईं |
| `FOREIGN_FILE_IN_GITDIR` | `refs/` या `objects/` में ऐसी फ़ाइल जो git ने नहीं बनाई (`desktop.ini`, `objects/` में `.tmp` फ़ाइलें) |
| `EMPTY_FILE_IN_GITDIR` | शून्य बाइट का ऑब्जेक्ट या ref |
| `GITDIR_COPY` | वर्कट्री में git डायरेक्टरी की कॉपी (`.git 2`) |
| `GIT_DIR_NOT_IGNORED` | git डायरेक्टरी दूसरे नाम से वर्कट्री के अंदर है (`.git.nosync`) और `git add -A` उसे कमिट कर देगा |
| `WORKTREE_ADMIN_BROKEN` | किसी लिंक्ड वर्कट्री ने अपनी एडमिन फ़ाइलें खो दी हैं |
| `STALE_OPERATION_STATE` | छूटी हुई rebase डायरेक्टरी git को लगवाती है कि rebase चल रहा है |
| `FSCK_ERRORS` | सिर्फ़ `--deep`: `git fsck` ने त्रुटियाँ बताईं (पूरा न होने पर वही कोड जानकारी बन जाता है) |
| `REFTABLE_TABLE_UNLISTED` | reftable रिपॉज़िटरी में ऐसी ref टेबल हैं जिन्हें उसकी सूची नहीं बताती: सिंक क्लाइंट द्वारा लाई गई दूसरे डिवाइस की टेबल, जिसकी सूची ऐसी कॉपी बन गई जिसे git कभी नहीं पढ़ता। अगला `git pack-refs` या मेंटेनेंस उन्हें, और उनके साथ उस डिवाइस की ब्रांचें, हटा देगा; पहले git डायरेक्टरी को सुरक्षित जगह कॉपी करें |
| `CHANGE_UNFINISHED` | gitbrella का कोई `fix`, `undo` या `move-out` पूरा नहीं हुआ (बीच में रोका गया); वहाँ git का उपयोग करने से पहले, उसे पूरा या रोलबैक करने के लिए बताया गया कमांड `--apply` के साथ चलाएँ |
| `GIT_DIR_RETURNED` | `move-out` के बाद `.git` फिर से डायरेक्टरी है (सिंक क्लाइंट पुराना वापस ले आया), इसलिए दो git डायरेक्टरी मौजूद हैं; कमिट करने से पहले तुलना करके एक रखें |
| `STAGED_CONFLICT_COPY` | index ऐसी फ़ाइल की सिंक कॉन्फ़्लिक्ट कॉपी जोड़ता है जिसे वह खुद भी सूचीबद्ध करता है (`notes.md` के पास `notes 2.md`, कॉपी की गई डायरेक्टरी `src 2/`, Syncthing के नाम); कमिट कॉपी को इतिहास में डाल देगा। सिर्फ़ नाम तय करते हैं; ऐसे नाम में बदलना और बिना मूल के कॉपी जैसे नाम वाली फ़ाइल नहीं गिनी जाती; स्प्लिट index में जाँचा नहीं जाता |

जानकारी (exit स्टेटस नहीं बदलता): `IN_CLOUD_FOLDER`, `GIT_DIR_NOT_SYNCED` (git डायरेक्टरी सिंक फ़ोल्डर से बाहर ले जाई गई है: सुरक्षित लेआउट), `WORKTREE_COPIES` (आपकी अपनी फ़ाइलों की कॉन्फ़्लिक्ट कॉपियाँ), `GIT_RUNNING`, `LOCK_IN_USE`, `LOCK_RECENT`, `IN_PROGRESS_OPERATION`, `UNKNOWN_IN_GITDIR`, `NO_CHECKOUT`, `PARTIAL_CLONE_UNVERIFIED`, `WORKTREE_SCAN_TRUNCATED`, `DEEP_CHECK_SKIPPED`, `REFTABLE_UNSUPPORTED`, `UNREADABLE_IN_GITDIR`, `PROCESS_CHECK_FAILED`, `GIT_DIR_IGNORE_UNCHECKED`, `GIT_TEMP_FILE`, `DATALESS_IN_ALTERNATE` (वैकल्पिक ऑब्जेक्ट स्टोर में सिर्फ़ क्लाउड वाली फ़ाइलें हैं, इसलिए ऑब्जेक्ट जाँचें छोड़ी गईं), `GC_PID_FOREIGN` (दूसरी मशीन का `gc.pid`: git 12 घंटे तक ऑटो gc छोड़ देता है), `GC_LOG_FRESH` (एक दिन से नया `gc.log` ऑटो gc रोकता है), `HOOKS_IN_SYNCED_FOLDER` (`core.hooksPath` या `core.fsmonitor` कमांड git डायरेक्टरी के बाहर सिंक फ़ोल्डर में है, इसलिए दूसरे डिवाइस पर किया गया बदलाव यहाँ चलता है), `WORKTREE_GUESSED` (`GIT_DIR` बिना वर्कट्री के और मौजूदा डायरेक्टरी में HEAD की कोई फ़ाइल नहीं: वर्कट्री नहीं जाँची गई)।

जब पाथ बिल्कुल भी रिपॉज़िटरी नहीं है, तो कारण डिस्क पर होने पर यह बताता है क्यों: नाम बदला हुआ `.git 2`, git की अपनी फ़ाइलें सिर्फ़ क्लाउड में, बिना HEAD की git डायरेक्टरी, ऐसी `.git` फ़ाइल जो अब न मौजूद git डायरेक्टरी की ओर इशारा करती है, या ऐसा `core.worktree` जो इस मशीन पर न मौजूद फ़ोल्डर की ओर इशारा करता है (सिंक क्लाइंट द्वारा लाई गई दूसरी मशीन की सेटिंग)। अगर पाथ में ऐसा `.git` है जिसका git उपयोग नहीं कर सकता, तो यह वहीं रुक जाता है (exit 2), बजाय इसके कि git की तरह किसी बाहरी रिपॉज़िटरी के बारे में जवाब दे।

<a name="install"></a>

## इंस्टॉल

git 2.31 या नया चाहिए। macOS और Linux, amd64 और arm64, cgo नहीं।

```
brew install aliyilmazco/tap/gitbrella
```

```
go install github.com/aliyilmazco/gitbrella/cmd/gitbrella@latest
```

या releases पेज से कोई आर्काइव लें।

### रिलीज़ सत्यापित करना

हर रिलीज़ के साथ `checksums.txt` (हर आर्काइव और SBOM का SHA-256), रिलीज़ वर्कफ़्लो द्वारा बनाया गया कीलेस cosign सिग्नेचर `checksums.txt.sigstore.json`, हर आर्काइव के लिए एक SPDX SBOM, और GitHub build-provenance attestation आता है। पहले सिग्नेचर जाँचें, फिर हस्ताक्षरित सूची से आर्काइव (उदाहरण Apple silicon के लिए v1.2.3 है)। cosign v3.1.3 या नया (v2 लाइन में v2.6.5) उपयोग करें: पुराने संस्करण नकली बंडल से धोखा खा सकते हैं (GHSA-fx35-mq7g-6g98)।

```sh
cosign verify-blob \
  --certificate-identity 'https://github.com/aliyilmazco/gitbrella/.github/workflows/release.yml@refs/tags/v1.2.3' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  --bundle checksums.txt.sigstore.json checksums.txt
grep ' gitbrella_1.2.3_darwin_arm64.tar.gz$' checksums.txt | shasum -a 256 -c
gh attestation verify gitbrella_1.2.3_darwin_arm64.tar.gz \
  --repo aliyilmazco/gitbrella \
  --signer-workflow aliyilmazco/gitbrella/.github/workflows/release.yml \
  --source-ref refs/tags/v1.2.3 --deny-self-hosted-runners
```

रिलीज़ किसी पुश किए गए टैग से `.github/workflows/release.yml` द्वारा `.goreleaser.yaml` के साथ बनाई जाती है और तब तक ड्राफ़्ट रहती है जब तक कोई व्यक्ति उसे प्रकाशित न करे। बाइनरी `-trimpath` और कमिट के समय के साथ बनती हैं, इसलिए एक ही टैग और एक ही Go रिलीज़ (वर्कफ़्लो सबसे नया 1.26 पैच लेता है) एक जैसी बाइनरी बनाते हैं; उनके चारों ओर के आर्काइव और SBOM में उनका बिल्ड समय होता है।

<a name="limits"></a>

## सीमाएँ

- `fix` सिर्फ़ वहीं ठीक करता है जहाँ एक ही सही उत्तर हो, और बाकी चलाने वाले कमांड के साथ आप पर छोड़ता है; स्थायी इलाज `move-out` है, जो `.git` को सिंक फ़ोल्डर से बाहर रखता है।
- iCloud खुद दो डिवाइसों के बीच जो कॉन्फ़्लिक्ट कॉपियाँ बनाता है, वे टेस्ट में दोबारा नहीं बनाई गईं; पहचान उन्हीं नामों वाली कॉपियों से टेस्ट की गई है।
- Codex अपने शेल टूल का `workdir` हुक को नहीं देता: Codex किसी दूसरे फ़ोल्डर में जो कमांड चलाता है, वह सेशन के फ़ोल्डर में जाँचा जाता है।
- Windows और Windows पर OneDrive टेस्ट नहीं किए गए। reftable रिपॉज़िटरी को फ़ाइल-स्तर की जाँचें और असूचीबद्ध टेबल की जाँच मिलती है; वहाँ ref कॉपियों की उनकी ब्रांचों से तुलना नहीं होती।
- ऐसे कॉपी नाम जिनके निशान कोई नाम जान-बूझकर रख सकता है, सिर्फ़ वहीं मिलाए जाते हैं जहाँ git खुद नाम बनाता है, वर्कट्री में कभी नहीं: Google Drive का `index (1)` git की अपनी फ़ाइलों और `refs/` में; OneDrive का `index-COMPUTER` OneDrive फ़ोल्डर के शीर्ष स्तर पर git की अपनी फ़ाइलों के लिए, ऐसे डिवाइस नाम के साथ जिसमें बड़ा अक्षर हो, जो ऐसा शब्द न हो जिससे लोग बैकअप का नाम खत्म करते हैं (`index-old`, `config-OLD`, `config-Backup`, `index-BAK` आपके हैं), और अधिकतम 15 अक्षर (लंबा Mac नाम छूट जाता है); पुराने Nextcloud का `_conflict-YYYYMMDD-HHMMSS`, Synology Drive के नाम, pCloud का `.conflicted` और Resilio का `.Conflict` शीर्ष स्तर पर git की अपनी फ़ाइलों के लिए (पुराने Nextcloud वाले Nextcloud फ़ोल्डर में मूल के पास `refs/` और `logs/` में भी)। किसी HEAD द्वारा बताई गई ब्रांच (किसी भी खाली जगह के साथ `ref:` के रूप में, या symlink के रूप में), उसका reflog, और उसे रखने वाली डायरेक्टरी कभी एक तरफ़ नहीं रखी जातीं, नाम चाहे जो हो। इसलिए `report (1).pdf`, `fix.Conflict` नाम की ब्रांच, `v1.0.conflicted` नाम का टैग, या `config-backup` साधारण नाम हैं।
- सबमॉड्यूल सबमॉड्यूल के अंदर से जाँचे जाते हैं। पैरेंट प्रोजेक्ट से, `.git/modules/<name>/` में कॉन्फ़्लिक्ट कॉपी तभी रिपोर्ट होती है जब उसका मूल उसके पास हो, और कॉपी जैसे नाम वाला सबमॉड्यूल (`lib 2`) कॉपी के रूप में रिपोर्ट होता है।
- लिंक्ड वर्कट्री का गायब index तब रिपोर्ट होता है जब वह वर्कट्री जाँची जाती है, मुख्य वर्कट्री नहीं।
- जब `.git` सिंक फ़ोल्डर के बाहर किसी स्टोर का symlink हो, तो git और जाँच लिंक किए गए वर्कट्री से चलाएँ। स्टोर डायरेक्टरी से, जिसमें कोई फ़ाइल नहीं होती, खाली हो चुका index जान-बूझकर किया गया "सब हटाओ" लगता है और कमिट नहीं रोकता।
- कुछ जान-बूझकर किए गए कमिट के लिए `--no-verify` चाहिए: डिस्क पर रहने वाली फ़ाइलों को अनट्रैक करना, जहाँ ऑब्जेक्ट नहीं पढ़े जाने चाहिए वहाँ हर फ़ाइल हटाना, किसी दूसरे hard link वाली फ़ाइल का सिर्फ़ केस या Unicode रूप बदलने वाला नाम परिवर्तन, और sparse checkout (cone मोड हो या न हो) में कोई भी कमिट जो किसी ट्रैक की गई फ़ाइल को हटाता है, नाम बदलता है, या टाइप बदलकर उसे हिलाता है (फ़ाइल जो डायरेक्टरी बन गई, डायरेक्टरी जो symlink या सबमॉड्यूल बन गई)। वहाँ git के sparse पैटर्न तय करते हैं कि कौन-सी फ़ाइलें डिस्क पर हैं, इसलिए जान-बूझकर हटाने को खोए हुए index से अलग नहीं किया जा सकता; पैटर्न पढ़े नहीं जाते।
- अगर सिंक क्लाइंट ने index के साथ खुद ब्रांच ref भी खो दिया (नया `packed-refs` आने से पहले उसकी loose फ़ाइल हट गई), तो HEAD नई ब्रांच जैसा दिखता है और कमिट नहीं रुकता: वह सिर्फ़ स्टेज की गई फ़ाइलों वाला नया इतिहास शुरू करता है। डिस्क पर कुछ नहीं हटता, और पुराना इतिहास reflog (`git reflog`) में बना रहता है।
- स्प्लिट index में, या जहाँ ऑब्जेक्ट नहीं पढ़े जाने चाहिए (2.45 से पुराने git पर आंशिक क्लोन, सिर्फ़ क्लाउड वाले alternates), index की HEAD से फ़ाइल-दर-फ़ाइल तुलना नहीं होती: सिर्फ़ गायब या खाली index पकड़ा जाता है।
- `core.splitIndex` के साथ, कोई फ़ाइल सूचीबद्ध न करने वाला index पहचाना नहीं जाता (उसका हेडर सिर्फ़ स्प्लिट हिस्सा गिनता है), इसलिए उससे किया गया कमिट नहीं रुकता।
- हुक: सिर्फ़ कमिट हुक उन्हें चलाने वाली git प्रोसेस से मिलते हैं। दूसरे हुक (`pre-push`, `pre-applypatch`) को जाँच वर्कट्री से चलानी होगी, नहीं तो उन्हें मना किया जाता है (exit 2)। जहाँ git प्रोसेस नहीं दिखती (ऐसा क्लाइंट जो हुक खुद चलाता है, या प्रोसेस सूची अवरुद्ध), जाँच मौजूदा डायरेक्टरी पर लौट आती है: तब, अगर git की डायरेक्टरी वर्कट्री की ओर वापस इशारा नहीं करती (`--separate-git-dir`, `.git.nosync`, `--work-tree`), तो बिना फ़ाइलों वाला index हमेशा कमिट रोकता है (जान-बूझकर खाली करने के लिए `--no-verify` उपयोग करें), HEAD की कोई फ़ाइल न रखने वाली मौजूदा डायरेक्टरी वर्कट्री के रूप में नहीं जाँची जाती (`WORKTREE_GUESSED`), और किसी दूसरी रिपॉज़िटरी या git डायरेक्टरी में जाने वाले हुक को मना किया जाता है (exit 2)। receive हुक (`pre-receive`) समर्थित गेट नहीं हैं।
- `move-out`: `.git` फ़ाइल हर टूल नहीं समझता। git और git चलाने वाले टूल काम करते हैं; isomorphic-git (मोबाइल पर Obsidian Git) और `.git` को डायरेक्टरी के रूप में खोलने वाले टूल नहीं।
- `move-out`: सिंक फ़ोल्डर का नाम बदलने या उसे हिलाने से रिलेटिव `.git` फ़ाइल टूट जाती है। तब `check` गायब डायरेक्टरी का नाम बताता है; फ़ोल्डर वापस रखें या `.git` फ़ाइल को हाथ से git डायरेक्टरी की ओर करें।
- `move-out` के लिए ज़रूरी है कि सिंक फ़ोल्डर हर डिवाइस पर होम के नीचे उसी जगह हो (iCloud Drive हमेशा होता है; Dropbox एक डिवाइस पर `~/Dropbox` और दूसरे पर `~/Library/CloudStorage/Dropbox` हो सकता है)। जब ऐसा नहीं होता, तो वहाँ `.git` फ़ाइल कहीं और इशारा करती है और `--attach` मना करता है (`TARGET_UNEXPECTED`)।
- स्थानांतरित git डायरेक्टरी होम फ़ाइल सिस्टम पर रहती है; उसे कहीं और रखने का कोई विकल्प नहीं है।
- `move-out --prepare` डिवाइस का उस समय का इतिहास कॉपी करता है: तैयारी के तुरंत बाद, बीच में कोई नया कमिट किए बिना, स्थानांतरण करें।
- `move-out` और `fix` iCloud Drive के अपने फ़ोल्डर में आज़माए गए हैं, किसी ऐप के iCloud फ़ोल्डर (Obsidian का `iCloud~md~obsidian`) के अंदर नहीं।
